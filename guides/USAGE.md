# 사용 안내

**한국어** · [English](USAGE.en.md)

[README의 첫 사용](../README.md#첫-작업-맡기기) 다음에 필요한 안내입니다. 설치·업데이트·제거는 [설치 안내](INSTALL.md)에 있습니다.

## 명령 보내기

아래 명령은 터미널이 아니라 **에이전트 대화에** 보냅니다. `<요청>`은 하고 싶은 일로, `<goal>`은 Spec이 알려 준 목표 폴더 이름으로 바꿉니다.

| 할 일 | Claude Code | Codex |
| --- | --- | --- |
| 목표 문서 작성 | `/spec <요청>` | `$spec <요청>` |
| 구현 시작 | `/seal docs/specs/<goal>` | `$seal docs/specs/<goal>` |

Claude Code에서 같은 이름의 명령과 겹치면 `/spec:spec <요청>`과 `/seal:seal docs/specs/<goal>`을 씁니다. Codex에서는 `$`를 치고 목록에서 `spec:spec` 또는 `seal:seal`을 고릅니다. `@Spec`은 플러그인 언급이며 Spec의 지침을 불러오지 않으므로 목표 문서만 쓴다는 보장이 없습니다.

## 목표를 고치거나 이어 가기

Spec은 목표와 범위, 완료 조건을 `docs/specs/<goal>/SPEC.md`에 바로 저장하고, 쓴 내용과 스스로 정한 결정·출처를 보고한 뒤 멈춥니다. "구현까지 해줘"라고 함께 말해도 목표 문서만 씁니다. 보고를 읽고 답하거나 수정을 요청하면 같은 문서를 고칩니다. Spec이 제안한 결정은 사용자가 받아들이거나 그 목표의 구현을 요청하면 사용자의 결정이 됩니다.

같은 동작을 다루는 목표가 이미 있는데 작성 대상을 정하지 않았다면, Spec은 새 목표로 쓸지 기존 목표를 고칠지 먼저 묻습니다. 결과를 바꾸는 결정이 남으면 문서를 `Status: Draft`로 두고 질문합니다. `Status: Ready`는 문서가 준비됐다는 표시이며 구현은 별도의 시작 요청으로 맡깁니다.

Seal에는 시작 명령 대신 `docs/specs/<goal> 구현해줘`라고 말해도 됩니다. 작업 중에는 매 단계 승인하지 않고, 결과를 바꾸는 결정이나 사람이 직접 확인해야 하는 항목에 답합니다.

대화가 끊겼다면 같은 프로젝트 폴더의 새 대화에서 다음과 같이 보냅니다. Seal이 저장된 목표·계획·진행 기록과 현재 상태를 확인하고 남은 일을 이어 갑니다.

```text
docs/specs/<goal> 이어서 해줘
```

## 완료 보고 읽기

완료 보고는 대화와 목표 폴더의 `PROGRESS.md`에 남습니다. 먼저 바뀐 결과와 무엇을 확인했는지 읽습니다. 필수 완료 조건은 검사 기록 또는 필요한 사용자 확인으로 충족돼야 합니다. 선택 조건은 완료를 막지 않으며 보고에서 구분합니다. 자동 검사는 에이전트가 작성합니다.

완료의 근거는 `ha done`이 남긴 완료 기록입니다. 보증 수준 `local`은 그 컴퓨터에서 얻은 근거라는 뜻입니다. 같은 사용자 권한의 에이전트가 검사와 기록을 바꿀 수 있으므로 독립된 제3자의 검증을 뜻하지 않습니다. 가정, 바뀐 검사, 남은 한계와 실제 결과를 함께 확인합니다. 자세한 확인 순서는 [운영 안내](OPERATIONS.md#완료-보고-읽기)에 있습니다.

빠진 것이 있으면 무엇을 고칠지 말합니다. Seal이 재작업 요청을 기록하고 다시 진행합니다. 목표 문서부터 바꿔야 한다면 Spec으로 고친 뒤, 별도로 계속하라고 요청합니다.

현재 Seal의 기본 결과는 로컬 변경과 commit(변경 이력을 저장한 단위)까지입니다. push·PR은 사용자가 직접 하거나 일반 에이전트에 별도로 요청할 수 있습니다. Jaekit은 독립된 검증 환경이나 무인 운영 기능을 제공하지 않습니다.

## 저장되는 파일

목표 폴더는 `docs/specs/<goal>/`입니다. Spec의 `SPEC.md`와 Seal의 `PLAN.md`, `REVIEW.md`, `PROGRESS.md`, `runs.jsonl`, 필요한 `tasks/` 파일은 Git으로 관리하고 commit합니다. 각각 목표, 계획, 계획 검토, 진행·완료 보고, 실행 기록, 작업별 설명을 담습니다. commit은 로컬에 이력을 저장하는 일이며 공개 전송은 별도입니다. 기록에는 사용자 발화와 작업 경로가 들어갈 수 있으므로 공개 저장소에 보내기 전에 내용을 확인합니다.

검사 출력 원문은 Git이 추적하지 않는 `.git/ha/`에 남으므로 `.gitignore`에 더할 것은 없습니다. linked worktree(Git 이력을 공유하는 별도 작업 폴더)에서는 `git rev-parse --absolute-git-dir`이 알려 주는 Git 폴더 아래 `ha/`에 있습니다. 출력은 로컬에만 있으며 확인이 필요하면 터미널에서 `ha log <goal> <seq>`를 실행합니다. 여기서 `<goal>`은 목표 경로, `<seq>`는 보고에 나온 기록 번호입니다.

## 문제 해결

| 증상 | 할 일 |
| --- | --- |
| `ha: command not found` 또는 기대한 버전이 아니다 | [버전 확인](INSTALL.md#버전-확인)에서 설치 여부와 실제 실행 파일을 확인합니다 |
| Claude Code에서 `/spec`이 다른 명령으로 실행된다 | 정식 이름 `/spec:spec <요청>`, `/seal:seal docs/specs/<goal>`을 씁니다 |
| 예전 `spec`·`seal` 플러그인이 대신 동작한다 | `claude plugin list`로 찾고 `claude plugin disable <plugin>`으로 끕니다. `<plugin>`은 목록에서 확인한 이전 플러그인 이름입니다. Codex는 `~/.codex/config.toml`의 해당 플러그인을 `enabled = false`로 둡니다 |
| Codex의 `@Spec`이 기대와 다르게 동작한다 | `$spec <요청>`으로 부릅니다. `$` 목록에서 `spec:spec`을 고릅니다 |
| `Cannot add marketplace "jaekit"` 오류가 난다 | 같은 이름이 이미 등록되어 있습니다. [로컬 경로 등록에서 옮기기](INSTALL.md#로컬-경로-등록에서-옮기기)를 따릅니다 |
| Seal이 멈추고 정할 것을 묻는다 | 질문에 답합니다. 답을 인용해 기록한 뒤 이어 갑니다. 직접 확인해야 하는 완료 조건도 있을 수 있습니다 |
| 인증 만료·권한 거부·사용량 한도로 멈췄다 | 원인을 해소한 뒤 `docs/specs/<goal> 이어서 해줘`라고 보냅니다. 같은 실패를 반복하지 않습니다 |
| 예산을 다 썼다며 멈췄다 | 보고된 남은 일을 읽고, 검증 횟수나 작업 시간 한도를 늘려 계속할지 정해서 말합니다. Seal은 그 말을 기록한 뒤 이어 갑니다 |

판단 이유와 재개 규칙은 [운영 안내](OPERATIONS.md)의 사용자 확인 및 막힘·예산 절에서 자세히 설명합니다.
