# 사용 안내

**한국어** · [English](USAGE.en.md)

목표를 고치거나, 끊긴 일을 이어 가거나, Seal의 질문에 답하거나, 완료 보고를 읽을 때 펴 보는 문서입니다. 목표 하나를 맡기고 끝낼 때까지의 순서로 적었습니다.

처음이라면 [Jaekit 이해하기](OVERVIEW.md)와 [README의 첫 작업 맡기기](../README.ko.md#첫-작업-맡기기)를 먼저 읽으세요. 설치·업데이트·제거는 [설치 안내](INSTALL.md)에 있습니다. 보고·검토 gate·비용·예산이 정확히 어떻게 동작하는지는 [세부 동작과 규칙](RULES.md)에 모았습니다.

## 명령 보내기

아래 명령은 터미널이 아니라 **에이전트 대화에** 보냅니다. `<요청>`은 하고 싶은 일로 바꿉니다. `<goal>`은 Spec이 알려 준 목표 폴더 이름으로 바꿉니다.

| 할 일 | Codex | Claude Code |
| --- | --- | --- |
| 목표 문서 작성 | `$spec:spec <요청>` | `/spec:spec <요청>` |
| 구현 시작 | `$seal:seal docs/specs/<goal>` | `/seal:seal docs/specs/<goal>` |

Codex에서는 `$`를 입력하고 Jaekit에서 설치한 `spec:spec` 또는 `seal:seal`을 고른 뒤 요청을 이어 씁니다.

`@Spec`은 플러그인 언급입니다. 언급만으로는 목표 문서만 쓰는 Spec의 지침이 골라진다는 보장이 없습니다. 확실하게 고르려면 위의 스킬 호출을 씁니다.

> **에이전트가 Spec을 부를 때.** 두 경우입니다. "이거 jaekit으로 해줘"처럼 Jaekit이나 목표 문서로 일하자고 할 때, 그리고 검토 지적이 요구사항을 바꿔야만 풀릴 때입니다. 이때 Spec은 `Proposed-By: agent` 줄이 있는 `Draft` 문서나 `amendments/` 아래의 수정안을 쓰고, 받아들일지 묻습니다. 평범한 구현 요청이나 버그 제보에는 부르지 않습니다. 누가 불렀든 `Ready`와 구현 시작은 사용자의 말로만 일어납니다.

<details>
<summary>스킬 이름과 호출 접두사</summary>

`spec:spec`은 **플러그인 이름:스킬 이름**입니다. 예전 설치본과 이름이 겹쳐서 붙는 접두사가 아니며, Jaekit만 설치했어도 이 이름을 사용합니다.

Codex는 `$`, Claude Code는 `/`로 호출합니다. 직접 설치한 단독 스킬의 짧은 이름이나 다른 에이전트의 호출법까지 같다고 가정하지 않습니다.

[Codex 플러그인 이름 규칙](https://developers.openai.com/plugins/build/plugins#create-a-plugin-manually), [Codex의 스킬 호출 예시](https://learn.chatgpt.com/docs/security/plugin/code-changes#automate-reviews-in-cicd), [Claude Code 스킬 위치와 이름](https://code.claude.com/docs/en/skills#choose-where-skills-load)을 참고하세요.

</details>

## 목표를 고치거나 이어 가기

### Spec은 저장 후 멈춤

Spec은 목표와 범위, 완료 조건을 `docs/specs/<goal>/SPEC.md`에 바로 저장합니다. 그리고 쓴 내용과 스스로 정한 결정·출처를 보고하고 멈춥니다. 보고를 읽고 답하거나 고쳐 달라고 하면 같은 문서를 고칩니다.

"구현까지 해줘"라고 함께 말해도 목표 문서만 씁니다. Spec이 제안한 결정은 사용자가 받아들이거나 그 목표의 구현을 요청할 때 사용자의 결정이 됩니다.

같은 동작을 다루는 목표가 이미 있고 어디에 쓸지 정하지 않았다면, Spec은 새 목표로 쓸지 기존 목표를 고칠지 먼저 묻습니다.

- `Status: Draft`: 결과를 바꾸는 결정이 남아 있으며 Spec이 질문합니다.
- `Status: Ready`: 문서가 준비됐다는 표시입니다. 그 자체로 구현을 시작하지 않습니다.
- `Assurance:`: 구현할 때 받아야 하는 독립 검토의 정도입니다. `light`는 작은 수정, `standard`는 보통의 변경에 씁니다. `strict`는 공개 계약·저장 데이터·권한·구성 요소 사이 경계를 바꾸는 목표에 씁니다. Spec이 등급을 제안하고 이유를 보고합니다. 다른 등급을 원하면 "strict로 해줘"처럼 말합니다.

### 구현은 별도 요청으로 시작

결과를 바꾸는 결정이 남지 않으면, Spec은 보고 끝에 지금 구현할지 묻습니다. 목표 경로와 등급도 함께 알립니다. 여기에 "응"이라고 답하면 구현이 시작됩니다.

- 답에 고칠 것을 함께 적으면("응, 그런데 AC-2는 빼줘") Spec이 먼저 문서를 고치고 다시 묻습니다.
- 구현 시작 명령도 그대로 쓸 수 있습니다. 시작 명령 대신 `docs/specs/<goal> 구현해줘`라고 말해도 됩니다.
- 작업 중에는 단계마다 승인하지 않습니다. 결과를 바꾸는 결정이나 사람이 직접 확인할 항목에만 답합니다.

대화가 끊겼다면 같은 프로젝트 폴더의 새 대화에서 다음과 같이 보냅니다. Seal이 저장된 목표·계획·진행 기록과 지금 상태를 확인하고 남은 일을 이어 갑니다.

```text
docs/specs/<goal> 이어서 해줘
```

> **이전 배포판으로 시작한 목표.** 이 안내는 v0.1.9로 새로 시작한 목표를 기준으로 합니다. 이전에 시작한 목표는 시작할 때의 규칙으로 계속 판정됩니다. 규칙 사이의 차이는 [세부 동작과 규칙](RULES.md)과 [실행 기록 계약](../contracts/run-record.md)에 있습니다.

## Seal의 시작 전 확인과 검토 순서

Seal은 시작하기 전에 미리 알 수 있는 결정을 한 번에 묻습니다. 작업 중에는 새로 생긴 질문만 묻습니다. 아래는 언제 무엇을 묻는지, 그리고 검토 등급에 따라 독립 검토가 어떤 순서로 붙는지입니다.

### 시작 전에 묻는 것

- **예산 질문은 한 번.** 요청에 예산이 없으면 Seal이 PLAN에 `검증 실행: 자동`을 씁니다. 산정 값이 미리 승인한 상한 안이면 묻지 않고 시작합니다. 넘으면 산정 값과 상한을 보이며 한 번 묻습니다.
  - 답한 숫자가 PLAN에 들어가고, 같은 PLAN에 같은 질문을 다시 하지 않습니다.
  - Seal은 `ha.json`을 쓰거나 고치지 않습니다.
- **시작 전 환경 점검.** 검사가 브라우저·DB·컨테이너·외부 서비스를 쓰면 Seal이 PLAN의 `## 실행 환경`에 적습니다. 그리고 baseline을 기록하기 전과, 재개 뒤 첫 검사 전에 `ha doctor`를 돌립니다. 쓸 수 없는 도구는 한 질문으로 모아 묻습니다. 권한이나 설정을 스스로 넓히지 않습니다.
- **시작 전 질문은 한 메시지로.** baseline을 기록하기 전에, 사용자의 말이 필요한 결정을 모아 한 메시지로 묻습니다. 목표 문서·계획·프로젝트 지침·코드를 읽어 미리 알 수 있는 결정입니다. 물을 것이 없으면 아무것도 묻지 않고 바로 일합니다.
  - 보호 경로의 파일을 바꾸는 계획, 요청이 허락하지 않은 기존 시험의 변경, 목표 문서와 코드가 어긋나 보이는 곳, 쓸 수 없는 도구, 승인이 필요한 예산이 그런 예입니다.
  - 질문마다 추천을 앞에 둔 선택지와, 답이 바꾸는 것을 밝힙니다.
  - 사용자 확인으로만 충족할 조건이 있으면, 끝에 무엇을 확인해 달라고 할지도 같은 메시지에서 알립니다.
  - 계획이 새로 만들 시험·검사 파일은 처음부터 `바꿀 수 있는 경로`에 들어갑니다. 그래서 나중에 범위 확인을 묻지 않습니다.

### 작업 중에 묻는 것과 보고

- **시작 뒤 질문은 생길 때.** 미리 알 수 없던 질문은 생겼을 때 묻습니다. 검토에서 나온 `requirement-question`이나 라운드 상한이 그런 질문입니다. 같은 때 기다리는 질문은 한 메시지로 묻습니다. 끝에 필요한 사용자 확인도 결과가 생긴 뒤 한 메시지로 모아 묻습니다.
  - 권한 밖의 변경이나 검사를 약하게 하는 변경은, 미리 물었다는 것만으로 확인되지 않습니다.
  - 미리 받은 답은 그 답이 허락한 변경을 commit한 뒤, 답을 인용해 확인으로 기록합니다. 그 변경은 다시 묻지 않습니다.
  - 확인한 내용이 그 뒤 다시 바뀌면 새 변경이므로 다시 묻습니다.
- **다섯 줄 보고.** `PROGRESS.md`는 `ha report`를 씁니다. `## 현재` 맨 위에는 `ha report`의 도장이 그대로 들어갑니다. Seal이 시각을 손으로 적지 않습니다.
  - `## 완료 보고`는 맨 위 다섯 줄(`바뀐 것`, `확인한 것`, `직접 볼 것`, `남은 한계`, `다음 행동`)부터 읽습니다. 그 아래에 완료 기록과 Seal의 판단 문장이 있습니다. 완료한 목표에서는 판단 문장이 `## 검수 요약`에 있습니다.
  - 한국어로 요청하면 `--lang ko`로 만듭니다.

### 검토 등급에 따른 순서

SPEC의 `Assurance:` 줄이 독립 검토 단계를 정합니다. 검토하는 방법은 Spar가 정하고, 검토 시점과 지적 처리는 Seal이 정합니다.

| 등급 | 받는 검토 |
| --- | --- |
| `light` | 독립 검토를 생략할 수 있고, 생략하면 이유를 `REVIEW.md`와 완료 보고에 남깁니다 |
| `standard` | 최종 후보의 candidate 라운드와 검토 수정 뒤 목표의 base commit부터 새 head까지의 candidate 라운드. `ha done` 전의 마지막 candidate 라운드가 누적 라운드입니다 |
| `strict` | `standard`에 더해 baseline 전 plan 라운드 한 번. 검사 계획만이 아니라 제품의 불변식과 결정 규칙도 봅니다. 그 뒤 목표 문서나 검사가 바뀌면 다음 candidate 라운드가 그때의 목표 문서를 검토합니다. SPEC.md나 연결된 목표 문서가 바뀌었으면 `review_docs_stale`이 풀리도록 사용자의 말로 plan 상한을 연장해 plan 라운드를 한 번 더 받습니다 |

**누적 라운드**는 목표의 base commit부터 마지막 head까지 전체를 다시 보는 candidate 라운드입니다. 검토 수정 뒤의 candidate 라운드 가운데, 열린 `defect`·`requirement-question` 없이 끝난 마지막 라운드가 누적 라운드입니다. 첫 candidate 라운드 뒤에 검토 수정이 없었으면 그 라운드가 누적 라운드입니다. 독립 검토를 받는 목표에서 Seal은 이 라운드 뒤에만 `ha done`을 실행합니다.

- 프로젝트 지침(`AGENTS.md` 등)이 더 많은 검토를 요구하면 그쪽을 따르고 완료 보고에 적습니다.
- 줄이 없는 목표는 이전처럼 선택된 보증 정책을 따릅니다.
- 완료 뒤 원격 리뷰를 반영해 달라고 하면 이 순서로 진행합니다: `reopen`, 수정, 누적 라운드, 낡은 검사의 재기록, `ha done`.

## 완료 보고 읽기

먼저 바뀐 결과와 무엇을 확인했는지 읽습니다. 완료 보고는 대화와 목표 폴더의 `PROGRESS.md`에 남습니다.

**검수 요약.** 완료 기록 뒤 `## 현재` 바로 다음의 `## 검수 요약`이 검수를 시작하는 곳입니다.

- 맨 위 줄: 완료 기록, 보증 등급, 충족한 필수 조건 수, 검토 gate 결과, 이 변경이 하는 일, 먼저 볼 것.
- 그 아래: 바뀐 것, 근거, 직접 볼 것, 보지 않은 것이 이 순서로 옵니다. 해당하는 것이 없는 항목에는 `없음`을 씁니다.
- 사용자의 언어로 씁니다. 기록이 무엇인지를 먼저 쓰고, 항목마다 짧게 씁니다. seq는 보조로만 붙입니다.
- 검증 출력과 지적 원문은 옮기지 않습니다. 지적은 ID, 한 줄 요약, 끝만 적습니다.
- Seal의 판단은 이 절에만 있습니다. `## 완료 보고`에는 `ha report` 출력과 이 절을 가리키는 한 줄이 있습니다.
- 목표를 다시 열어 완료를 다시 기록하면, 새 완료 기록 기준으로 다시 씁니다.

완료한 목표는 `## 검수 요약`부터 읽습니다. 멈춘 목표는 `## 완료 보고`를 읽습니다.

- 필수 완료 조건은 검사 기록, 필요한 사용자 확인, 또는 `review` 조건이면 검토 gate로 충족돼야 합니다.
- 선택 조건은 완료를 막지 않으며 보고에서 구분합니다.
- 자동 검사는 에이전트가 작성합니다.

### 결과에 따라 할 일

`ha status`나 `ha done`의 결과를 보고 다음에 할 일을 찾습니다. 괄호 안 숫자는 종료 코드입니다.

> `ha status`의 `complete`만으로는 완료가 아닙니다. 출력에 완료 기록이 나올 때까지는 Seal이 `ha done`으로 완료를 기록합니다.

| `ha status` 결과 (종료 코드) | 누가 | 할 일 |
| --- | --- | --- |
| `complete` (0), 완료 기록이 아직 없음 | Seal | `ha done`으로 완료를 기록합니다. |
| `complete` (0), 완료 기록 `seq N` | 나 | 결과를 확인합니다. |
| `incomplete` (1) | Seal | 계속 작업합니다. 기다리면 됩니다. |
| `needs_user` (2) | 나 | 질문에 답합니다. |
| `blocked` (3) | 나 | 원인을 해소한 뒤 `docs/specs/<goal> 이어서 해줘`를 보냅니다. |
| `budget_exhausted` (4) | 나 | 예산을 정합니다. |
| 오류 (64 이상) | 나 | 오류 메시지를 읽고 [문제 해결](#문제-해결)을 봅니다. |

64 이상은 작업 상태가 아니라 오류입니다.

- 64: 사용법 오류
- 65: 시작하지 않은 목표나 끊긴 기록 같은 거절
- 66: Core가 지원하지 않는 규칙 버전
- 70: 내부 오류

메시지를 읽고 [문제 해결](#문제-해결)을 봅니다.

### 완료 근거와 재작업

가정, 바뀐 검사, 남은 한계와 실제 결과를 함께 확인합니다. 완료의 근거는 `ha done`이 남긴 완료 기록입니다.

보증 수준 `local`은 그 컴퓨터에서 얻은 근거라는 뜻입니다. 같은 사용자 권한의 에이전트는 검사와 기록을 바꿀 수 있습니다. 그래서 독립된 제3자의 검증을 뜻하지 않습니다.

자세한 확인 순서는 [운영 안내](OPERATIONS.md#완료-보고-읽기)에 있습니다.

빠진 것이 있으면 무엇을 고칠지 말합니다. Seal이 재작업 요청을 기록하고 다시 진행합니다. 목표 문서부터 바꿔야 한다면 Spec으로 고친 뒤, 따로 계속하라고 요청합니다.

지금 Seal의 기본 결과는 로컬 변경과 commit(변경 이력을 저장한 단위)까지입니다. push·PR은 직접 하거나 일반 에이전트에 따로 요청합니다. Jaekit은 독립된 검증 환경이나 무인 운영 기능을 제공하지 않습니다.

## 저장되는 파일

목표와 기록은 `docs/specs/<goal>/`에서 확인합니다.

| 파일 | 작성 주체 | 담는 내용 |
| --- | --- | --- |
| `SPEC.md` | Spec | 목표, 범위, 완료 조건 |
| `PLAN.md` | Seal | 계획 |
| `REVIEW.md` | Seal | 계획 검토 |
| `PROGRESS.md` | Seal | 진행·검수 요약(`## 검수 요약`)·완료 보고 |
| `runs.jsonl` | `ha` | 실행 기록 |
| 필요한 `tasks/` 파일 | Seal | 작업별 설명 |

- **Git 추적:** 프로젝트 정책을 따릅니다. 추적하는 프로젝트에서는 commit합니다. 비공개·ignore 정책이면 로컬에 두고, 강제로 Git에 추가하지 않습니다.
- **공개 전송 전:** commit은 로컬에 이력을 저장하는 것이고, 공개 전송은 따로입니다. 기록에는 사용자 발화와 작업 경로가 들어갈 수 있습니다. 공개 저장소에 보내기 전에 내용을 확인합니다.
- **Jaekit의 정책:** 이 저장소 자체의 비공개 `docs/` 정책은 다른 프로젝트의 필수 설정이 아닙니다.
- **출력 원문:** 검사 출력은 로컬에만 있습니다. Git이 추적하지 않는 `.git/ha/`에 남으므로 `.gitignore`에 더할 것은 없습니다.
- **Linked worktree:** Git 이력을 공유하는 별도 작업 폴더에서는 `git rev-parse --absolute-git-dir`이 알려 주는 Git 폴더 아래 `ha/`에 출력이 있습니다.
- **출력 확인:** 터미널에서 `ha log <goal> <seq>`를 실행합니다. `<goal>`은 목표 경로, `<seq>`는 보고에 나온 기록 번호입니다.
- **실행 시간:** `ha timing <goal>`로 어느 검사가 오래 걸렸는지, 시간 제한에 얼마나 가까웠는지 봅니다. 시간 보기(capability `run-timing/v1`)를 지원하는 Core가 필요합니다. 측정 세부 사항은 아래에 있습니다.

<details>
<summary>실행 시간: 측정값과 한계</summary>

시간 보기를 지원하는 Core는 검사 기록마다 다음을 남깁니다.

- 적용한 시간 제한.
- 제한 구간 경과와 제한 발동 여부.
- 운영체제가 주는 CPU 시간.

`ha timing <goal>`은 이 값을 표로, `--format json`은 `timing/v1` 문서로 보여 줍니다. 보기는 검사를 실행하지 않고 기록을 바꾸지 않습니다.

제한 구간은 제한 타이머가 켜진 때부터 프로세스 종료를 확인했거나 시간 초과를 결정한 때까지입니다. 그 뒤의 정리 시간은 들어가지 않습니다.

이 값은 측정값일 뿐 완료 판정과 예산에는 쓰이지 않습니다. 실행 시간의 합은 겹친 실행을 더한 값이라 목표 경과 시간이나 예산이 아닙니다.

CPU는 운영체제마다 세는 범위가 달라 운영체제 사이에 같은 뜻으로 비교하지 않습니다.

| 운영체제 | CPU 범위 |
| --- | --- |
| macOS·Linux | 실행한 프로세스와 그것이 기다린 하위 프로세스 |
| Windows | Job Object 안의 모든 프로세스 |

측정하지 못한 CPU는 0이 아니라 측정 불가나 측정 실패로 보입니다. 이 기능 전에 기록한 검사는 "기록되지 않음"으로 보입니다.

</details>

## 문제 해결

| 증상 | 할 일 |
| --- | --- |
| `ha: command not found` 또는 기대한 버전이 아니다 | [버전 확인](INSTALL.md#버전-확인)에서 설치 여부와 실제 실행 파일을 확인합니다 |
| 스킬이 안 보이거나 짧은 이름이 다른 명령을 실행한다 | 설치 후 에이전트를 새로 엽니다. 위 표의 전체 이름을 쓰고, Codex에서는 `$` 목록에서 Jaekit의 스킬을 고릅니다 |
| 예전 `spec`·`seal` 설치본이 함께 보인다 | 아래 절차로 이전 설치본을 제거하고 에이전트를 새로 엽니다 |
| Codex의 `@Spec`이 기대와 다르게 동작한다 | `$` 목록에서 Jaekit의 `spec:spec`을 고르고 요청을 보냅니다 |
| `Cannot add marketplace "jaekit"` 오류가 난다 | 같은 이름이 이미 등록되어 있습니다. [로컬 경로 등록에서 옮기기](INSTALL.md#로컬-경로-등록에서-옮기기)를 따릅니다 |
| Seal이 멈추고 정할 것을 묻는다 | 질문에 답합니다. 답을 인용해 기록한 뒤 이어 갑니다. 직접 확인해야 하는 완료 조건도 있을 수 있습니다 |
| 인증 만료·권한 거부·사용량 한도로 멈췄다 | 원인을 해소한 뒤 `docs/specs/<goal> 이어서 해줘`라고 보냅니다. 같은 실패를 반복하지 않습니다 |
| 검사 전에 미커밋 변경 때문에 거부됐다 | 출력된 경로와 tracked/untracked·symlink 표시를 확인하고 작업 의도에 따라 정리합니다. 실행하지 않은 검사는 횟수에 들어가지 않습니다. [실행 전 안내](OPERATIONS.md#실행-전에-확인할-것)를 참고합니다 |
| 시작 전에 검증 예산이 부족하다고 나온다 | `ha estimate docs/specs/<goal>`의 최소량·상한·부족량을 확인합니다. 시작 전에 충분한 예산이나 목표 분할을 결정합니다 |
| 시작이 `exceeds the pre-approved limit`로 멈췄다 | 산정한 횟수를 승인할지 정합니다. 승인하면 그 숫자를 PLAN `검증 실행`에 쓰거나 `ha.json`의 `preapproved_runs`를 올립니다. [자동 예산](RULES.md#자동-예산)을 봅니다 |
| `pre-approved run limit` 오류로 멈췄다 | 출력된 `ha.json` 경로와 이유를 보고 파일을 `{"preapproved_runs": <정수>}` 형식으로 고치거나 지웁니다 |
| 예산을 다 썼다며 멈췄다 | 남은 일을 읽고 계속할지 정합니다. 아래 예산 세부 사항을 참고합니다 |
| Seal이 Core 호환성 때문에 멈췄다 | 확인한 실행 파일과 부족한 지원을 읽습니다. [업데이트 안내](INSTALL.md#업데이트)에 따라 v0.1.9 조합을 설치한 뒤 실제 선택된 Core의 지원 정보를 다시 확인합니다. 자동 설치나 구규칙 전환으로 우회하지 않습니다 |

<details>
<summary>이전 설치본 제거</summary>

| 에이전트 | 설치 목록 확인 | 이전 설치본 제거 |
| --- | --- | --- |
| Codex | `codex plugin list` | `codex plugin remove <plugin>` |
| Claude Code | `claude plugin list` | `claude plugin uninstall <plugin>` |

`<plugin>`에는 이전 설치본의 ID를 넣고, `spec@jaekit`·`seal@jaekit`·`spar@jaekit`은 유지합니다. 직접 복사한 스킬도 있다면 해당 설치 폴더를 별도로 정리하고 에이전트를 새로 엽니다.

</details>

<details>
<summary>예산 변경과 재개</summary>

- 횟수 총상한은 사용자 동의와 문맥을 기록해 바꿀 수 있습니다. 쓴 횟수와 시간 한도는 그대로입니다.
- 시간 상한 변경은 지원하지 않습니다.
- 새 창이 필요하면 명시적 재개를 요청합니다.

</details>

판단 이유와 재개 규칙은 [운영 안내](OPERATIONS.md)의 사용자 확인 및 막힘·예산 절에서 자세히 설명합니다.

`ha report`의 표지, 실행 환경 점검, 검토 gate, baseline 선택, 비용 보기, 자동 예산, 자율 처리, 검증 보고 형식, 배포판과 규칙은 [세부 동작과 규칙](RULES.md)에 있습니다.
