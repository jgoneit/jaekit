# 사용 안내

**한국어** · [English](USAGE.en.md)

[README의 첫 사용](../README.md#첫-작업-맡기기) 다음에 필요한 안내입니다. 설치·업데이트·제거는 [설치 안내](INSTALL.md)에 있습니다.

현재 배포판 v0.1.3은 ha 0.1.3·spec 0.1.11·seal 0.1.9·기본 규칙 `/3` 조합입니다. 실행 전 거부·횟수 추정, `/3` 결과 분류와 예산 정책이 적용됩니다. 기존 목표는 저장된 규칙을 유지합니다. [버전별 적용 범위](INSTALL.md#배포판과-개발-조합)를 확인합니다.

## 명령 보내기

아래 명령은 터미널이 아니라 **에이전트 대화에** 보냅니다. `<요청>`은 하고 싶은 일로, `<goal>`은 Spec이 알려 준 목표 폴더 이름으로 바꿉니다.

| 할 일 | Codex | Claude Code |
| --- | --- | --- |
| 목표 문서 작성 | `$spec:spec <요청>` | `/spec:spec <요청>` |
| 구현 시작 | `$seal:seal docs/specs/<goal>` | `/seal:seal docs/specs/<goal>` |

Codex에서는 `$`를 입력하고 Jaekit에서 설치한 `spec:spec` 또는 `seal:seal`을 고른 뒤 요청을 이어 씁니다. `@Spec`은 플러그인 언급입니다. 목표 문서만 쓰는 Spec의 지침을 명확히 선택하려면 위의 스킬 호출을 사용합니다. 플러그인 언급만으로 같은 지침이 선택된다는 보장이 없습니다.

`spec:spec`은 **플러그인 이름:스킬 이름**입니다. 예전 설치본과 이름이 겹쳐서 붙는 접두사가 아닙니다. Jaekit만 설치했어도 이 이름을 사용합니다. Codex는 `$`, Claude Code는 `/`로 호출합니다. 직접 설치한 단독 스킬의 짧은 이름이나 다른 에이전트의 호출법까지 같다고 가정하지 않습니다. [Codex 플러그인 이름 규칙](https://developers.openai.com/plugins/build/plugins#create-a-plugin-manually), [Codex의 스킬 호출 예시](https://learn.chatgpt.com/docs/security/plugin/code-changes#automate-reviews-in-cicd), [Claude Code 스킬 위치와 이름](https://code.claude.com/docs/en/skills#choose-where-skills-load)을 참고하세요.

## 목표를 고치거나 이어 가기

Spec은 목표와 범위, 완료 조건을 `docs/specs/<goal>/SPEC.md`에 바로 저장하고, 쓴 내용과 스스로 정한 결정·출처를 보고한 뒤 멈춥니다. "구현까지 해줘"라고 함께 말해도 목표 문서만 씁니다. 보고를 읽고 답하거나 수정을 요청하면 같은 문서를 고칩니다. Spec이 제안한 결정은 사용자가 받아들이거나 그 목표의 구현을 요청하면 사용자의 결정이 됩니다.

같은 동작을 다루는 목표가 이미 있는데 작성 대상을 정하지 않았다면, Spec은 새 목표로 쓸지 기존 목표를 고칠지 먼저 묻습니다. 결과를 바꾸는 결정이 남으면 문서를 `Status: Draft`로 두고 질문합니다. `Status: Ready`는 문서가 준비됐다는 표시이며 구현은 별도의 시작 요청으로 맡깁니다.

Seal에는 시작 명령 대신 `docs/specs/<goal> 구현해줘`라고 말해도 됩니다. 작업 중에는 매 단계 승인하지 않고, 결과를 바꾸는 결정이나 사람이 직접 확인해야 하는 항목에 답합니다.

대화가 끊겼다면 같은 프로젝트 폴더의 새 대화에서 다음과 같이 보냅니다. Seal이 저장된 목표·계획·진행 기록과 현재 상태를 확인하고 남은 일을 이어 갑니다.

```text
docs/specs/<goal> 이어서 해줘
```

## 완료 보고 읽기

완료 보고는 대화와 목표 폴더의 `PROGRESS.md`에 남습니다. 먼저 바뀐 결과와 무엇을 확인했는지 읽습니다. 필수 완료 조건은 검사 기록 또는 필요한 사용자 확인으로 충족돼야 합니다. 선택 조건은 완료를 막지 않으며 보고에서 구분합니다. 자동 검사는 에이전트가 작성합니다.

완료의 근거는 `ha done`이 남긴 완료 기록입니다. 보증 수준 `local`은 그 컴퓨터에서 얻은 근거라는 뜻입니다. 같은 사용자 권한의 에이전트가 검사와 기록을 바꿀 수 있으므로 독립된 제3자의 검증을 뜻하지 않습니다. 가정, 바뀐 검사, 남은 한계와 실제 결과를 함께 확인합니다. 자세한 확인 순서는 [운영 안내](OPERATIONS.md#완료-보고-읽기)에 있습니다.

빠진 것이 있으면 무엇을 고칠지 말합니다. Seal이 재작업 요청을 기록하고 다시 진행합니다. 목표 문서부터 바꿔야 한다면 Spec으로 고친 뒤, 별도로 계속하라고 요청합니다.

현재 Seal의 기본 결과는 로컬 변경과 commit(변경 이력을 저장한 단위)까지입니다. push·PR은 사용자가 직접 하거나 일반 에이전트에 별도로 요청할 수 있습니다. Jaekit은 독립된 검증 환경이나 무인 운영 기능을 제공하지 않습니다.

## 저장되는 파일

목표 폴더는 `docs/specs/<goal>/`입니다. Spec의 `SPEC.md`와 Seal의 `PLAN.md`, `REVIEW.md`, `PROGRESS.md`, `runs.jsonl`, 필요한 `tasks/` 파일은 각각 목표, 계획, 계획 검토, 진행·완료 보고, 실행 기록, 작업별 설명을 담습니다. Git 추적 여부는 프로젝트 정책에 따릅니다. 추적하는 프로젝트에서는 commit합니다. 비공개·ignore 정책이면 로컬에 보관하고 강제로 Git에 추가하지 않습니다. commit은 로컬 이력 저장이며 공개 전송은 별도입니다. 기록에는 사용자 발화와 작업 경로가 들어갈 수 있으므로 공개 저장소에 보내기 전에 내용을 확인합니다. Jaekit 저장소 자체의 비공개 `docs/` 정책은 다른 프로젝트의 필수 설정이 아닙니다.

검사 출력 원문은 Git이 추적하지 않는 `.git/ha/`에 남으므로 `.gitignore`에 더할 것은 없습니다. linked worktree(Git 이력을 공유하는 별도 작업 폴더)에서는 `git rev-parse --absolute-git-dir`이 알려 주는 Git 폴더 아래 `ha/`에 있습니다. 출력은 로컬에만 있으며 확인이 필요하면 터미널에서 `ha log <goal> <seq>`를 실행합니다. 여기서 `<goal>`은 목표 경로, `<seq>`는 보고에 나온 기록 번호입니다.

## 문제 해결

| 증상 | 할 일 |
| --- | --- |
| `ha: command not found` 또는 기대한 버전이 아니다 | [버전 확인](INSTALL.md#버전-확인)에서 설치 여부와 실제 실행 파일을 확인합니다 |
| 스킬이 안 보이거나 짧은 이름이 다른 명령을 실행한다 | 설치 후 에이전트를 새로 엽니다. 위 표의 전체 이름을 쓰고, Codex에서는 `$` 목록에서 Jaekit의 스킬을 고릅니다 |
| 예전 `spec`·`seal` 설치본이 함께 보인다 | Codex는 `codex plugin list`로 확인하고 `codex plugin remove <plugin>`으로 제거합니다. Claude Code는 `claude plugin list`와 `claude plugin uninstall <plugin>`을 씁니다. `<plugin>`에는 이전 설치본의 ID를 넣고, `spec@jaekit`·`seal@jaekit`은 유지합니다. 직접 복사한 스킬도 있다면 해당 설치 폴더를 별도로 정리하고 에이전트를 새로 엽니다 |
| Codex의 `@Spec`이 기대와 다르게 동작한다 | `$` 목록에서 Jaekit의 `spec:spec`을 고르고 요청을 보냅니다 |
| `Cannot add marketplace "jaekit"` 오류가 난다 | 같은 이름이 이미 등록되어 있습니다. [로컬 경로 등록에서 옮기기](INSTALL.md#로컬-경로-등록에서-옮기기)를 따릅니다 |
| Seal이 멈추고 정할 것을 묻는다 | 질문에 답합니다. 답을 인용해 기록한 뒤 이어 갑니다. 직접 확인해야 하는 완료 조건도 있을 수 있습니다 |
| 인증 만료·권한 거부·사용량 한도로 멈췄다 | 원인을 해소한 뒤 `docs/specs/<goal> 이어서 해줘`라고 보냅니다. 같은 실패를 반복하지 않습니다 |
| 검사 전에 미커밋 변경 때문에 거부됐다 | 출력된 경로와 tracked/untracked·symlink 표시를 확인하고 작업 의도에 따라 정리합니다. 실행하지 않은 검사는 횟수에 들어가지 않습니다. [실행 전 안내](OPERATIONS.md#실행-전에-확인할-것)를 참고합니다 |
| 시작 전에 검증 예산이 부족하다고 나온다 | `ha estimate docs/specs/<goal>`의 최소량·상한·부족량을 확인합니다. 시작 전에 충분한 예산이나 목표 분할을 결정합니다 |
| 예산을 다 썼다며 멈췄다 | 남은 일을 읽고 계속할지 정합니다. `/3`은 사용자 동의와 문맥을 기록해 횟수 총상한을 바꾸며 쓴 횟수·시간 한도를 유지합니다. 시간 상한 변경은 지원하지 않습니다. 새 창이 필요하면 명시적 재개를 요청합니다. 기존 `/1`·`/2`는 원래 한도의 새 창을 여는 재개 규칙을 유지합니다 |
| Seal이 Core 호환성 때문에 멈췄다 | 확인한 실행 파일과 부족한 지원을 읽습니다. [업데이트 안내](INSTALL.md#업데이트)에 따라 v0.1.3 조합을 설치한 뒤 실제 선택된 Core의 지원 정보를 다시 확인합니다. 자동 설치나 구규칙 전환으로 우회하지 않습니다 |

판단 이유와 재개 규칙은 [운영 안내](OPERATIONS.md)의 사용자 확인 및 막힘·예산 절에서 자세히 설명합니다.

## 소스의 보고 형식

Seal 0.1.10 소스는 기대 결과의 근거, 관측 경계, 시험 방법·대체 환경과 미확인 범위를 기존 검토·보고에서 구분합니다. 조건 그룹이 같은 설명을 참조할 수 있으며, 실제 수행과 예정은 다릅니다. 기존 목표 형식과 현재 배포판은 그대로입니다. [자세한 보고 경계](OPERATIONS.md#소스의-검증-근거-보고)를 참고하세요.
