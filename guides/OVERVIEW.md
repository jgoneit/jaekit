# Jaekit 이해하기

**한국어** · [English](OVERVIEW.en.md)

Jaekit을 처음 알아볼 때 가장 먼저 읽는 문서입니다. Jaekit이 어떤 문제를 풀려고 하는지, 목표 하나가 어떻게 지나가는지, 완료 기록이 무엇을 뜻하고 무엇은 뜻하지 않는지를 처음부터 끝까지 이어서 설명합니다. 다 읽은 뒤에는 [설치 안내](INSTALL.md)로 설치하고 [README의 첫 작업 맡기기](../README.ko.md#첫-작업-맡기기)를 따라 해 봅니다.

## 에이전트가 "다 했습니다"라고 할 때

Claude Code나 Codex에 일을 맡기면 이런 일을 자주 겪습니다.

- 조건 열 개 중 일곱 개만 하고 끝냅니다.
- 어려운 조건을 쉬운 조건으로 바꿔 읽습니다.
- 일찍 멈춰서 "빠진 것 마저 해줘"를 되풀이하게 됩니다.
- "테스트를 통과했습니다"라고 하지만, 무엇을 어떻게 확인했는지는 바뀐 코드를 처음부터 읽어야 압니다.

대화가 끊기면 무엇을 약속했고 어디까지 확인했는지 다시 설명해야 합니다.

흔한 해결책은 두 가지입니다.

- **절차로 묶기.** 하나는 계획 형식, 단계마다 승인, 행동을 막는 장치로 에이전트를 절차에 묶는 것입니다. 그러면 모델이 좋아질수록 절차가 오히려 한계가 되고, 도구가 에이전트의 모든 행동을 막는다고 증명하기도 어렵습니다.
- **보고를 믿기.** 다른 하나는 에이전트의 보고를 믿는 것입니다. 하지만 에이전트는 자기 검사를 고칠 수 있고 쉬운 기준을 쓸 수 있습니다.

"테스트 통과"는 "목표 달성"과 같지 않습니다.

## Jaekit의 생각: 일은 맡기고, 끝은 기록으로

Jaekit은 그 사이를 고릅니다. 세 가지만 붙잡고 나머지는 에이전트에게 맡깁니다.

1. **목표는 내가 정합니다.** 무엇을 하면 끝인지, 즉 완료 조건을 일을 시작하기 전에 문서로 정합니다. 구현하는 동안 에이전트는 이 문서를 고치지 않습니다.
2. **일은 에이전트가 합니다.** 계획, 순서, 도구는 에이전트가 정합니다. 단계마다 승인하지 않고, 결과를 바꾸는 결정이 필요할 때만 묻습니다.
3. **완료는 기록으로 판단합니다.** 완료 조건마다 검사를 돌린 기록이 있어야 완료가 남습니다. 새로 생기는 동작이라면 그 검사가 바꾸기 전에는 실패하고 바꾼 뒤에는 통과해야 합니다. 처음부터 통과하는 검사는 아무것도 확인하지 않기 때문입니다.

## 목표 하나가 지나가는 길

로그인 화면에 "비밀번호 찾기" 링크를 더하는 **가상 예시**로 따라가 봅니다. 실제로 실행하거나 검증한 사례가 아닙니다.

아래에 나오는 Spec·Seal·`ha`·Spar는 Jaekit을 이루는 부분의 이름입니다. 내가 터미널에서 하나씩 실행하는 도구가 아닙니다. 대화에서 `/spec:spec`으로 부르거나 "응"이라고 답하면, 에이전트가 단계마다 맞는 부분을 씁니다. 각자 하는 일은 다음 절에 정리했습니다.

1. **요청합니다.** 에이전트 대화에 `/spec:spec 로그인 화면에 "비밀번호 찾기" 링크를 추가해줘`라고 보냅니다(Codex는 `$spec:spec`).
2. **Spec이 목표를 씁니다.** `docs/specs/password-link/SPEC.md`에 목표와 완료 조건을 적습니다. 예를 들어 `AC-1` "로그인 화면에 재설정 페이지로 가는 링크가 보인다", `AC-2` "기존 로그인은 그대로 동작한다"입니다. 검토 등급도 제안하고, 지금 구현할지 한 번 물은 뒤 멈춥니다.
3. **확인하고 "응"이라고 답합니다.** 빠진 조건이 있으면 고쳐 달라고 하고, 맞으면 "응"이라고 답합니다. 그때부터 Seal이 시작됩니다.
4. **Seal이 계획합니다.** `PLAN.md`에 조건마다 검사 방법을 적습니다. `AC-1`은 새로 생기는 동작이고, `AC-2`는 계속 지켜야 하는 동작입니다.
5. **`ha`가 검사하고 기록합니다.** 에이전트는 `AC-1`의 검사를 바꾸기 전의 코드에서 먼저 돌려 실패하는 것을 기록합니다. 그다음 구현하고 다시 돌려 통과를 기록합니다. `AC-2`는 통과 기록을 남깁니다. 모든 실행은 `runs.jsonl`에 한 줄씩 쌓입니다.
6. **Spar가 독립 검토를 합니다.** 이 목표의 등급은 `standard`라서, 완료 전에 다른 맥락의 리뷰어들이 변경을 검토합니다. 고칠 지적이 있으면 에이전트가 고치고, 끝난 검토를 gate로 기록합니다.
7. **`ha done`이 완료를 기록합니다.** 필수 조건이 모두 기록으로 충족되면 완료 기록이 남고, 보고가 `PROGRESS.md`에 붙습니다.
8. **보고를 읽습니다.** 바뀐 것, 확인한 것, 직접 볼 것, 남은 한계, 다음 행동 다섯 줄과 조건별 근거를 보고, 실제 결과도 함께 확인합니다.

중간에 대화가 끊기면 같은 프로젝트의 새 대화에서 `docs/specs/password-link 이어서 해줘`라고 보냅니다. 새 대화의 에이전트가 목표 폴더와 `ha`가 계산한 상태를 읽고 남은 일을 이어 갑니다.

## 누가 무엇을 하나요

| 누구 | 하는 일 |
| --- | --- |
| 나 | 원하는 일을 말하고, 목표 문서를 확인하고, 결과를 바꾸는 결정에 답하고, 완료 보고를 읽습니다 |
| 에이전트 (Claude Code·Codex) | 판단하고 계획하고 구현하는 유일한 주체입니다. Spec과 Seal은 에이전트가 읽는 지침입니다 |
| Spec | 요청을 목표 문서로 정리합니다. 목표, 범위, 완료 조건, 검토 등급을 쓰고 멈춥니다. 구현하지 않습니다 |
| Seal | 확인한 목표대로 에이전트가 계획·구현·검사·수정을 끝까지 이어 가게 합니다. 목표 문서는 읽기만 합니다 |
| `ha` | 터미널 프로그램입니다. 검사를 실행해 모든 실행을 기록하고, 그 기록만으로 상태와 완료를 계산합니다. 모델을 부르지 않습니다 |
| Spar | 작업한 에이전트의 대화 밖에 있는 리뷰어들(기본은 claude·codex·agy CLI)에게 같은 자료를 보내 독립 검토를 받고, 지적과 그 처리를 기록합니다 |

`ha`와 Spar는 에이전트가 실행합니다. 내가 터미널에 입력하는 것은 설치와 업데이트 명령뿐이고, 일은 에이전트 대화로 맡깁니다.

## 무엇이 남나요

목표마다 프로젝트 안에 폴더 하나가 생깁니다.

| 파일 | 쓰는 쪽 | 담는 것 |
| --- | --- | --- |
| `SPEC.md` | Spec | 목표, 범위, 완료 조건. 나의 문서입니다 |
| `PLAN.md` | Seal | 조건마다 검사하는 방법, 바꿀 수 있는 범위, 실행 예산 |
| `REVIEW.md` | Seal | 검토 계획과 Spar 기록의 요약 |
| `PROGRESS.md` | Seal | 진행 상태와 완료 보고 |
| `runs.jsonl` | `ha` | 덧붙이기만 하는 실행 기록 |

완료 보고의 맨 위 다섯 줄은 `ha`가 실행 기록, Git, 목표 문서로 계산한 값입니다. 에이전트가 고쳐 쓰지 않습니다. 읽는 법은 [사용 안내](USAGE.md#완료-보고-읽기)에 있습니다.

## 검토 등급

목표 문서의 `Assurance:` 줄이 독립 검토를 얼마나 받을지 정합니다. Spec이 변경의 크기와 위험을 보고 제안하고, 다른 등급을 원하면 "strict로 해줘"처럼 말합니다.

| 등급 | 쓰는 곳 | 받는 검토 |
| --- | --- | --- |
| `light` | 오타나 문구 하나 같은 작은 수정 | 이유를 남기고 독립 검토를 건너뛸 수 있습니다 |
| `standard` | 보통의 변경 | 완료 전에 Spar 검토 라운드를 받습니다 |
| `strict` | 공개 계약, 저장 데이터, 권한, 구성 요소 사이 경계를 바꾸는 목표 | 작업 전 계획 검토도 받습니다 |

Spar를 처음 쓰기 전에는 프로젝트 준비가 한 가지 필요합니다. [README의 첫 `standard` 목표 전에](../README.ko.md#첫-standard-목표-전에)를 봅니다. 리뷰어에게 무엇이 전송되는지는 [Spar 안내](SPAR.md#컴퓨터-밖으로-나가는-것)에 있습니다.

## 완료가 뜻하는 것과 뜻하지 않는 것

완료 기록이 있다는 것은 다음을 뜻합니다.

- 필수 완료 조건마다 검사 기록 또는 필요한 사용자 확인이 있습니다.
- 새 동작의 검사는 바꾸기 전에 실패하고 바꾼 뒤에 통과한 기록이 있습니다.
- `standard`·`strict` 목표는 기록된 검토 gate가 마지막 commit을 덮습니다.

다음은 뜻하지 않습니다.

- **결과 전체에 결함이 없다는 것.** 검사가 목표를 충분히 덮는지는 프로그램이 자동으로 판단할 수 없습니다. 그래서 독립 검토와 사용자 확인으로 보완합니다.
- **독립된 제3자의 검증.** 보증 수준은 `local`입니다. 검사는 에이전트가 작성하고, 같은 사용자 권한의 에이전트는 검사와 기록 파일을 바꿀 수 있습니다. 기록의 연결은 실수로 고친 것을 드러낼 뿐 위조를 막지는 않습니다.
- **배포와 설치.** 기본 결과는 로컬 변경과 commit까지입니다. push, PR, 배포는 따로 하거나 일반 에이전트에 요청합니다.

Jaekit은 에이전트를 가두는 도구가 아니라, 무엇이 실제로 확인됐고 무엇이 확인되지 않았는지를 드러내는 도구입니다.
