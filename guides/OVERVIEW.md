# Jaekit 이해하기

**한국어** · [English](OVERVIEW.en.md)

Jaekit은 Claude Code나 Codex에 맡긴 일이 정말 끝났는지 기록으로 확인하게 해 주는 도구입니다. 무엇을 하면 끝인지 먼저 문서로 정하고, 끝났는지는 에이전트의 말 대신 실제로 돌린 검사의 기록으로 판단합니다.

처음 보는 사람을 위한 안내입니다. 다 읽은 뒤에는 [설치 안내](INSTALL.md)로 설치하고 [README의 첫 작업 맡기기](../README.ko.md#첫-작업-맡기기)를 따라 해 보세요.

## 에이전트가 "다 했습니다"라고 할 때

Claude Code나 Codex에 일을 맡기면 이런 일이 생기곤 합니다.

- 조건 열 개 중 일곱 개만 하고 끝냅니다.
- 어려운 조건을 쉬운 조건으로 바꿔 읽습니다.
- 일찍 멈춰서 "빠진 것 마저 해줘"를 되풀이하게 됩니다.
- "테스트를 통과했습니다"라고 하지만, 무엇을 확인했는지는 코드를 다 읽어야 압니다.
- 대화가 끊기면 무엇을 약속했는지 처음부터 다시 설명합니다.

단계마다 승인하면 이런 일은 줄지만, 일을 맡긴 의미가 줄어듭니다. 보고를 그대로 믿으면 편하지만, 에이전트는 자기 검사를 고치거나 쉬운 기준을 쓸 수 있습니다. "테스트 통과"가 "목표 달성"은 아닙니다.

## Jaekit의 생각: 일은 맡기고, 끝은 기록으로

Jaekit이 붙잡는 것은 세 가지뿐입니다. 나머지는 에이전트에게 맡깁니다.

1. **목표는 내가 정합니다.** 무엇을 하면 끝인지, 곧 완료 조건을 일을 시작하기 전에 문서로 정합니다. 일하는 동안 에이전트는 이 문서를 고치지 않습니다.
2. **일은 에이전트가 합니다.** 계획, 순서, 도구는 에이전트가 정합니다. 단계마다 승인받지 않고, 결과가 달라지는 결정만 묻습니다.
3. **완료는 기록으로 판단합니다.** 필수 완료 조건마다 검사를 돌린 기록이 있어야 완료가 남습니다. 자동으로 확인할 수 없는 조건은 내가 확인했다는 기록으로 채웁니다.

> **기록이 더 필요한 조건.** 이미 있는 버그를 고치는 조건과 "X가 일어나지 않는다" 같은 금지 조건은, 바꾸기 전 코드에서 검사가 실패한 기록도 있어야 합니다. 처음부터 통과하는 검사로는 고쳤는지 알 수 없기 때문입니다. 문서 내용에 관한 조건은 `standard`·`strict` 목표의 독립 검토로 채웁니다. 정확한 범위는 [완료가 뜻하는 것](#완료가-뜻하는-것과-뜻하지-않는-것)에 있습니다.

## 쓰면 무엇이 달라지나요

같은 일을 대화로만 맡길 때와 Jaekit으로 맡길 때를 나란히 놓았습니다. 일은 어느 쪽이든 같은 에이전트가 합니다. 달라지는 것은 기록입니다.

| 이럴 때 | 대화로만 맡기면 | Jaekit으로 맡기면 |
| --- | --- | --- |
| 일을 시작할 때 | 무엇을 하면 끝인지가 대화 곳곳에 흩어집니다 | 완료 조건을 먼저 문서로 정하고, 내가 확인한 뒤에 시작합니다 |
| 검사를 돌리면 | "통과했습니다"라는 말만 남습니다 | 어느 commit에서 무슨 명령을 돌려 어떤 결과가 났는지 한 줄씩 남습니다 |
| 코드를 또 고치면 | 앞의 "통과"가 지금 코드에도 맞는지 알 수 없습니다 | 앞의 기록은 남지만 근거로 세지 않습니다. 지금 코드에서 다시 검사합니다 |
| 처음부터 통과하는 검사 | 새 동작이 생겼는지 가려내지 못해도 통과로 보입니다 | 버그 수정이나 금지 조건은 바꾸기 전에 실패한 기록이 있어야 근거가 됩니다 |
| 기존 테스트를 고치면 | 테스트를 느슨하게 고쳐도 "통과"로 보입니다 | 허락하지 않은 테스트 변경이나 테스트를 약하게 만드는 변경은 내가 확인할 때까지 완료를 막습니다 |
| 목표나 범위가 바뀌면 | 바뀐 줄 모르고 넘어갈 수 있습니다 | 목표 문서나, 바꿔도 된다고 정한 범위 밖의 파일이 바뀌면 내가 확인할 때까지 완료를 막습니다 |
| 대화가 끊기면 | 처음부터 다시 설명합니다 | 새 대화에서 "이어서 해줘"라고 하면 목표 폴더와 기록을 읽고 이어 갑니다 |
| "다 됐습니다" | 끝났는지가 말로 정해집니다 | `ha`가 기록과 문서, Git을 보고 완료인지 계산해 남깁니다 |

## 누가 무엇을 하나요

일하는 주체는 쓰던 에이전트 하나입니다. Spec과 Seal은 에이전트가 따르는 지침이고, `ha`와 Spar는 에이전트가 실행하는 도구입니다. 그래서 "Spec이 쓴다"는 에이전트가 Spec의 지침대로 쓴다는 뜻입니다.

| 누구 | 하는 일 |
| --- | --- |
| 나 | 원하는 일을 말하고, 목표 문서를 확인하고, 결정에 답하고, 완료 보고를 읽습니다 |
| 에이전트 (Claude Code·Codex) | 판단하고 계획하고 구현합니다. 일하는 주체는 이것 하나입니다 |
| Spec | 요청을 목표 문서로 정리하는 지침입니다. 목표, 범위, 완료 조건, 검토 등급을 쓰고 멈춥니다 |
| Seal | 확인한 목표를 끝까지 가져가는 지침입니다. 계획·구현·검사·수정을 이어 가고, 목표 문서는 읽기만 합니다 |
| `ha` | 에이전트가 돌린 검사를 모두 기록하고, 그 기록과 문서, Git으로 완료를 계산하는 터미널 프로그램입니다. AI 모델을 부르지 않습니다 |
| Spar | 작업한 대화 밖의 리뷰어들(기본은 claude CLI, 설정하면 codex·agy도)에게 같은 자료를 보내 독립 검토를 받고, 지적과 처리를 기록합니다 |

Spec·Seal·Spar는 Claude Code나 Codex에 설치하는 플러그인이고, `ha`와 `spar`는 터미널 프로그램입니다.

## 목표 하나가 지나가는 길

로그인 화면에 "비밀번호 찾기" 링크를 더하는 **가상 예시**로 따라가 봅니다. 실제로 실행한 사례가 아닙니다.

1. **요청합니다.** 에이전트 대화에 `/spec:spec 로그인 화면에 "비밀번호 찾기" 링크를 추가해줘`라고 보냅니다. Codex에서는 `$spec:spec`입니다.
2. **Spec이 목표를 씁니다.** `SPEC.md`에 목표와 번호 붙은 완료 조건을 적습니다. 예를 들어 AC-1은 "로그인 화면에 재설정 링크가 보인다", AC-2는 "기존 로그인은 그대로 동작한다"입니다. 검토 등급도 제안합니다. 정할 것이 남지 않았으면 지금 구현할지 한 번 묻고 멈춥니다.
3. **확인하고 "응"이라고 답합니다.** 빠진 조건이 있으면 고쳐 달라고 합니다. 맞으면 "응"이라고 답합니다. 여기서부터 Seal이 일합니다.
4. **Seal이 계획합니다.** `PLAN.md`에 조건마다 무엇으로 검사할지 적습니다. AC-1은 새로 생길 동작이고, AC-2는 지켜야 할 동작입니다.
5. **`ha`가 검사를 기록합니다.** 에이전트가 검사를 돌릴 때마다 `ha`가 결과를 `runs.jsonl`에 한 줄씩 남깁니다. 이 예시에서는 AC-1을 바꾸기 전에 먼저 돌려 실패를 남기고, 구현한 뒤 다시 돌려 통과를 남깁니다. AC-2는 통과를 남깁니다.

   > 지금의 Seal(`run-rules/8`)에서 새 기능은 통과 기록만으로 충족됩니다. 바꾸기 전 실패 기록은 버그 수정과 금지 조건에만 필요합니다. 여기서는 기록의 모양을 보이려고 AC-1에도 남겼습니다.

6. **Spar가 독립 검토를 합니다.** 이 목표의 [검토 등급](#검토-등급)은 `standard`입니다. 그래서 완료 전에 작업한 대화 밖의 리뷰어들이 변경을 검토합니다. 고칠 지적은 에이전트가 고치고, 끝난 검토의 결과(검토 gate)를 기록합니다.
7. **`ha done`이 완료를 기록합니다.** 필수 조건이 모두 충족되고 검토 기록 같은 나머지 요건도 갖추면 완료 기록이 남습니다. 보고는 `PROGRESS.md`에 붙습니다.
8. **보고를 읽습니다.** `PROGRESS.md`의 검수 요약에 무엇이 바뀌었고, 무엇을 근거로 했고, 내가 직접 볼 것이 무엇인지 모여 있습니다. 그 아래에 `ha`가 계산한 완료 보고가 있습니다. 실제 결과도 함께 확인합니다.

대화가 끊기면 같은 프로젝트의 새 대화에서 `docs/specs/password-link 이어서 해줘`라고 보냅니다. 새 대화의 에이전트가 목표 폴더와 `ha`가 계산한 상태를 읽고 남은 일을 이어 갑니다.

## 무엇이 남나요

목표마다 프로젝트 안에 폴더 하나가 생깁니다. 모두 보통 파일입니다.

| 파일 | 쓰는 쪽 | 담는 것 |
| --- | --- | --- |
| `SPEC.md` | Spec | 목표, 범위, 완료 조건. 나의 문서입니다 |
| `PLAN.md` | Seal | 조건마다 검사하는 방법, 바꿀 수 있는 범위, 실행 예산 |
| `REVIEW.md` | Seal | 검토 계획과 Spar 기록의 요약 |
| `PROGRESS.md` | Seal | 진행 상태, 검수 요약, 완료 보고 |
| `runs.jsonl` | `ha` | 덧붙이기만 하는 실행 기록 |

**검수 요약.** 완료한 목표는 `PROGRESS.md`의 `## 검수 요약`부터 읽습니다. 맨 위에 완료 기록, 보증 등급, 충족한 필수 조건 수, 검토 결과가 있습니다. 그 아래에 바뀐 것, 근거, 직접 볼 것, 보지 않은 것이 차례로 옵니다. 쓰는 규칙은 [사용 안내](USAGE.md#완료-보고-읽기)에 있습니다.

완료 보고의 맨 위 다섯 줄은 `ha`가 실행 기록, Git, 목표 문서로 계산합니다. 에이전트가 고쳐 쓰지 않습니다. 보고에 나오는 낱말은 이렇게 읽습니다.

- `base`: 작업을 시작한 commit입니다.
- `seq`: 기록의 번호입니다. 완료 기록 `seq 6`은 완료를 남긴 여섯 번째 기록입니다.
- 보증 수준 `local`: 이 컴퓨터에서 얻은 근거라는 뜻입니다.
- 검사 작성자: 실행자: 구현한 에이전트가 검사도 직접 썼다는 뜻입니다.

## 검토 등급

목표 문서의 `Assurance:` 줄이 독립 검토를 얼마나 받을지 정합니다. Spec이 변경의 크기와 위험을 보고 제안합니다. 다른 등급을 원하면 "strict로 해줘"처럼 말합니다. 프로젝트 지침이 더 많은 검토를 요구하면 그쪽을 따릅니다.

| 등급 | 쓰는 곳 | 받는 검토 |
| --- | --- | --- |
| `light` | 오타나 문구 하나 같은 작은 수정 | 프로젝트 지침이 요구하지 않으면, 이유를 남기고 독립 검토를 건너뛸 수 있습니다 |
| `standard` | 보통의 변경 | 완료 전에 Spar 검토 라운드를 받습니다 |
| `strict` | 공개 계약, 저장 데이터, 권한, 구성 요소 사이 경계를 바꾸는 목표 | 작업 전 계획 검토도 받습니다 |

새로 시작한 `standard`·`strict` 목표는 Spar 검토 기록이 있어야 완료됩니다. 이전 버전으로 시작한 목표는 시작할 때의 규칙을 따릅니다. Spar를 처음 쓰기 전에는 프로젝트 준비가 하나 필요합니다. [README의 첫 `standard` 목표 전에](../README.ko.md#첫-standard-목표-전에)를 봅니다. 리뷰어에게 무엇이 전송되는지는 [Spar 안내](SPAR.md#컴퓨터-밖으로-나가는-것)에 있습니다.

## 완료가 뜻하는 것과 뜻하지 않는 것

완료 기록이 있다는 것은 다음을 뜻합니다.

- 필수 완료 조건마다 검사 기록이나 필요한 사용자 확인이 있습니다. `review` 조건이면 검토 gate가 있습니다.
- 새로 시작한 목표라면, `요구`를 표시한 필수 change 조건마다 그 검사가 바꾸기 전 코드에서 실패하고 바꾼 뒤에 통과한 기록이 있습니다. Seal은 이미 있는 버그를 고치는 조건과 금지 조건에 `요구`를 표시합니다. 표시하지 않은 change 조건은 통과 기록만으로 충족될 수 있습니다.
- 새로 시작한 `standard`·`strict` 목표는 완료를 기록할 때의 코드와 목표 문서를 검토한 Spar 기록(검토 gate)이 있습니다.

다음은 뜻하지 않습니다.

- **결과 전체에 결함이 없다는 것.** 검사가 목표를 충분히 덮는지는 프로그램이 판단할 수 없습니다. 그래서 독립 검토와 사용자 확인으로 보완합니다.
- **독립된 제3자의 검증.** 보증 수준은 `local`입니다. 검사는 에이전트가 쓰고, 같은 사용자 권한의 에이전트는 검사와 기록 파일을 바꿀 수 있습니다. 기록의 각 줄은 앞 줄의 해시를 담고 있어 앞선 기록을 고치거나 지운 것은 드러납니다. 하지만 마지막 줄의 변경이나 작정한 위조까지 막지는 못합니다.
- **배포와 설치.** 기본 결과는 로컬 변경과 commit까지입니다. push, PR, 배포는 따로 하거나 일반 에이전트에 요청합니다.

Jaekit은 에이전트를 감시하는 보안 도구가 아닙니다. 무엇이 실제로 확인됐고 무엇이 확인되지 않았는지를 드러내는 도구입니다.

## 자주 묻는 질문

**터미널과 에이전트 대화에는 각각 무엇을 입력하나요?**
터미널에는 주로 설치와 업데이트 명령을 입력합니다. 상태나 기록을 직접 볼 때와 Spar 리뷰어를 설정할 때도 씁니다. 에이전트 대화에는 `/spec:spec <요청>`(Codex는 `$spec:spec`), 목표를 확인한 뒤의 "응", 질문에 대한 답, 대화가 끊겼을 때의 `docs/specs/<goal> 이어서 해줘`를 보냅니다. `ha`와 `spar` 명령은 에이전트가 실행합니다.

**우리 프로젝트에 무엇이 생기나요?**
목표마다 `docs/specs/<goal>/` 폴더가 생깁니다. 이 폴더를 Git으로 추적할지는 프로젝트 정책을 따릅니다. 기록에는 내가 한 말과 작업 경로가 들어갈 수 있으니, 공개 저장소에 올리기 전에는 내용을 확인합니다. Spar를 쓰는 첫 `standard`·`strict` 목표 전에는 `.gitignore`에 `docs/reviews/`를 더합니다.

**이미 있는 테스트는 어떻게 쓰나요?**
기존 테스트 전체는 "기존 동작이 그대로인지"를 확인하는 검사로 쓸 수 있습니다. 어떤 조건을 무엇으로 검사할지는 에이전트가 `PLAN.md`에 적습니다. 자세한 형식은 [실행 묶음 계약](../contracts/bundle.md)에 있습니다.

**끝나면 push나 PR, 배포까지 해 주나요?**
아닙니다. 기본 결과는 로컬 변경과 commit까지입니다. push와 PR은 직접 하거나 일반 에이전트에 따로 요청합니다.

**우리 코드가 밖으로 나가나요?**
`ha`는 AI 모델을 부르지 않습니다. Spar 리뷰어는 기준·규칙 문서와 변경 내용(diff)을 각자의 제공자에게 보내고, 리뷰어가 읽은 프로젝트 파일도 함께 갈 수 있습니다. claude는 Anthropic, codex는 OpenAI, agy는 Google로 갑니다. 밖으로 나가면 안 되는 코드라면 Spar를 돌리지 않습니다. 자세한 내용은 [Spar 안내](SPAR.md#컴퓨터-밖으로-나가는-것)에 있습니다.
