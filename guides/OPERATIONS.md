# 작업 상태와 완료 보고 읽기

처음 쓰는 사람을 위한 호출·재개·문제 해결은 [사용 안내](USAGE.md)에 있습니다([English](USAGE.en.md)). 설치와 버전 확인은 [설치 안내](INSTALL.md)를 봅니다. 이 문서는 작업 중 질문과 완료 보고를 더 자세히 읽는 방법을 설명합니다.

## 목표 맡기기

Spec은 요청을 `docs/specs/<goal>/SPEC.md`에 목표·범위·완료 조건으로 정리하고 보고한 뒤 멈춥니다. 결과를 바꾸는 질문에 답하거나 고칠 것을 말해 목표를 다듬습니다. `Status: Ready`는 문서가 준비됐다는 표시이며 구현을 시작하지는 않습니다.

준비되면 Codex 대화에서 `$` 목록의 `seal:seal`을 골라 별도 메시지로 `$seal:seal docs/specs/<goal>`을 보냅니다. Claude Code에서는 `/seal:seal docs/specs/<goal>`을 씁니다. 이미 목표 문서가 있다면 바로 Seal에 맡겨도 됩니다. 에이전트가 계획·검사 방법을 검토하고 구현·검사·수정을 이어 갑니다. 매 작업마다 승인할 필요는 없습니다.

목표와 범위를 바꿀지는 사용자가 정합니다. Seal은 목표 문서를 고치지 않습니다. Spec으로 목표를 고쳤다면 별도로 `docs/specs/<goal> 이어서 해줘`라고 요청합니다. 자세한 문서 형식은 [목표 문서 계약](../contracts/goal-docs.md)과 [실행 묶음 계약](../contracts/bundle.md)에 있습니다.

## 완료 보고 읽기

완료 보고는 목표 폴더의 `PROGRESS.md`와 대화에 함께 나옵니다. 다음을 확인합니다.

1. **무엇이 바뀌었는가.** 실제 파일·화면·동작이 요청과 맞는지 봅니다.
2. **필수 조건이 어떻게 충족됐는가.** 자동 검사 결과와 직접 확인한 항목을 구분합니다. 선택 조건은 완료를 막지 않으며 따로 표시합니다.
3. **검사가 무엇을 다뤘는가.** 새 동작을 확인한 검사, 유지해야 할 동작, 확인하지 못한 범위를 봅니다. 검증 명령이나 조건 종류를 바꿨다면 이유를 확인합니다.
4. **가정과 한계가 무엇인가.** 에이전트가 정한 가정이 의도와 맞는지, 남은 한계가 결과에 영향을 주는지 봅니다.

완료의 근거는 `ha done`이 남긴 완료 기록입니다. 터미널에서 `ha status <goal>`로 현재 목표와 기록에 따른 상태를 확인할 수 있습니다. `<goal>`은 `docs/specs/login-link`처럼 실제 목표 폴더 경로로 바꿉니다.

보증 수준 `local`은 해당 컴퓨터에서 얻은 근거라는 뜻입니다. 검사는 실행한 에이전트가 작성하며 같은 사용자 권한으로 파일과 기록을 바꿀 수 있습니다. 결과 전체의 무결함이나 독립된 제3자의 보증을 뜻하지 않습니다.

빠진 것이 있으면 무엇을 고칠지 말합니다. Seal이 사용자 요청을 인용한 `reopen`을 기록하고 재작업합니다. 이전 완료 기록은 현재 완료 근거로 쓰이지 않으며 새 예산 창이 열립니다. 목표 문서부터 바꿔야 한다면 Spec으로 고친 뒤 별도로 계속하라고 요청합니다.

검사 출력 원문이 필요하면 터미널에서 `ha log <goal> <seq>`로 봅니다. `<seq>`는 보고에 나온 기록 번호입니다. 원문은 해당 작업 트리의 Git 디렉토리 아래 `ha/`에 있고 Git이 추적하지 않습니다([저장되는 파일](USAGE.md#저장되는-파일)).

## `needs_user` 처리

에이전트가 정할 수 없는 항목이 남으면 이유와 함께 묻습니다. 필요한 판단을 하고 답하면 그 답이 기록됩니다.

| 이유 | 확인할 것 | 이어 가는 방법 |
| --- | --- | --- |
| `manual_unconfirmed` | 자동 검사로 확인할 수 없는 조건을 직접 확인했는가 | 결과를 확인한 뒤 알려 줍니다. 조건 문장이 바뀌면 다시 확인해야 합니다 |
| `out_of_scope` | 계획 범위 밖의 변경이 필요한가 | 해당 변경을 허용하거나 되돌리게 합니다. 목표 자체가 바뀌면 Spec으로 고칩니다 |
| `test_definition_changed` | 기존 테스트 변경이 정당한가 | 변경 이유와 내용을 보고 허용하거나 되돌리게 합니다 |
| `spec_changed` | 목표 문서 변경이 의도한 것인가 | 의도한 변경이면 확인합니다. 고친 뒤 보낸 계속·구현 요청도 확인으로 기록됩니다 |
| `error_limit` | 같은 코드에서 검사 오류가 반복된 원인이 무엇인가 | 환경을 고친 뒤 다시 실행하게 합니다. 직접 확인할 조건으로 바꾸려면 먼저 목표를 검토합니다 |
| `record_integrity` | 실행 기록이 손상됐는가 | 원인을 확인합니다. 기록을 임의로 고쳐 통과시키지 말고, 필요하면 새 목표 폴더에서 시작합니다 |

## 막힘과 예산

- **`blocked`**: 인증 만료, 권한 거부, 사용량 한도 등으로 멈춘 상태입니다. 에이전트가 남긴 해소 조건을 읽고 원인을 해결한 뒤 계속하라고 합니다.
- **`budget_exhausted`**: 검사 횟수나 경과 시간의 예산을 넘은 상태입니다. 남은 일을 읽고 더 쓸지 정합니다. 허용하면 에이전트가 그 말을 인용한 `reopen`을 기록하고 새 예산 창을 엽니다.

예산은 마지막 시작이나 `reopen`부터 기록 시각으로 잽니다. 상태 조회만으로 시간이 늘지는 않지만, 기다린 뒤 같은 창에 새 기록이 붙으면 기다린 시간도 들어갑니다. 완료 기록이 있는 목표는 시간이 지나도 예산 초과 상태가 되지 않습니다. `run-rules/2`로 시작한 목표는 필수 조건이 모두 충족되고 예산 초과만 남았으면 완료를 기록할 수 있습니다([실행 기록 계약](../contracts/run-record.md)).

## 새 대화에서 이어 가기

같은 프로젝트 폴더에서 새 대화를 열고 `docs/specs/<goal> 이어서 해줘`라고 보냅니다. Seal이 목표·계획·진행 기록과 현재 상태를 읽고 남은 일을 이어 갑니다. 사용자 판단이 필요한 항목이 남아 있으면 먼저 답합니다.
