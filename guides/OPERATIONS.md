# 작업 상태와 완료 보고 읽기

**한국어** · [English](OPERATIONS.en.md)

작업이 왜 멈췄는지, 완료 보고가 무엇을 근거로 하는지 자세히 알고 싶을 때 읽는 문서입니다. 시작 전 점검, 수정 전 실패가 뜻하는 것, 완료 보고의 근거, 사용자 확인이 필요한 상태(`needs_user`), 막힘과 예산, 보증 정책을 다룹니다. 처음 쓰는 사람을 위한 호출·재개·문제 해결은 [사용 안내](USAGE.md)에 있습니다([English](USAGE.en.md)). 설치와 버전 확인은 [설치 안내](INSTALL.md)를 보세요.

이 문서는 v0.1.9(ha 0.1.9·spar 0.1.9·spec 0.1.16·seal 0.1.36·spar 플러그인 0.1.9)의 동작을 설명합니다. 실행 전 진단과 지원 확인, `nested/1`, `/3` 결과, 횟수 총상한 변경을 다룹니다. 기존 목표는 저장된 규칙과 형식을 유지합니다. 배포판과 소스 빌드의 차이는 [버전별 적용 범위](INSTALL.md#배포판과-개발-조합)에 있습니다.

## 목표 맡기기

Spec은 요청을 `docs/specs/<goal>/SPEC.md`에 정리합니다. 목표, 범위, 완료 조건을 적고 보고한 뒤 멈춥니다. 결과를 바꾸는 질문에 답하거나 고칠 것을 말해 목표를 다듬습니다. `Status: Ready`는 문서가 준비됐다는 표시입니다. 구현을 시작하지는 않습니다.

준비되면 Codex 대화에서는 `$` 목록의 `seal:seal`을 고른 뒤, 별도 메시지로 `$seal:seal docs/specs/<goal>`을 보냅니다. Claude Code에서는 `/seal:seal docs/specs/<goal>`을 씁니다. 목표 문서가 이미 있다면 바로 Seal에 맡겨도 됩니다. 에이전트는 계획과 검사 방법을 검토한 뒤 구현, 검사, 수정을 이어 갑니다. 작업마다 승인할 필요는 없습니다.

목표와 범위를 바꿀지는 사용자가 정합니다. Seal은 목표 문서를 고치지 않습니다. Spec으로 목표를 고쳤다면 `docs/specs/<goal> 이어서 해줘`라고 따로 요청합니다. 문서 형식은 [목표 문서 계약](../contracts/goal-docs.md)과 [실행 묶음 계약](../contracts/bundle.md)에 자세히 있습니다.

## 도구 미리 점검하기

검사가 브라우저나 외부 도구를 쓴다면, 검사를 실제로 돌리기 전에 그 도구가 있는지 확인합니다. PLAN의 `## 실행 환경` 절에 `` - <이름>: `<점검 명령>` `` 형식으로 도구를 적고 `ha doctor <goal>`을 실행합니다.

결과는 도구마다 `사용 가능` 또는 `사용 불가`입니다. 사용 불가의 이유는 `실행 파일 없음`, `실행 권한 없음`, `시간 초과`, `0이 아닌 종료`, `신호로 종료` 중 하나입니다. 점검은 도구 하나에 60초까지입니다. 점검은 기록과 예산에 들어가지 않습니다. `ha doctor`는 도구를 설치하지 않습니다. 사용 불가인 도구는 검사 전에 설치하거나 경로를 고칩니다.

## 실행 전에 확인할 것

Seal은 기록을 남기기 전에 세 가지를 봅니다.

- 설치된 `ha`가 필요한 기능을 갖췄는지
- 예산이 충분한지
- 작업 트리에 커밋하지 않은 변경이 없는지

하나라도 어긋나면 Seal은 멈추고 이유를 알립니다.

### Core 지원

Seal 0.1.20부터는 Core 지원을 손으로 대조하지 않습니다. Seal은 skill 폴더의 `core-requirements.json`에 필요한 지원을 선언하고, `ha start --check-skill`로 시작합니다. 빠진 지원이 있으면 `ha`가 기록 없이 거부합니다. 그러면 Seal은 실행 파일과 메시지를 알리고 멈춥니다.

- Seal 0.1.21은 `run-rules/5`와 검토 gate 지원도 요구합니다.
- 설치된 `ha`가 `run-rules/5`나 Seal이 요구하는 다른 지원을 모르면, Seal은 기록 없이 멈춥니다. 이전 규칙으로 물러나지 않습니다. 할 일은 그 지원을 갖춘 `ha`를 설치하는 것입니다.
- 이미 시작한 목표에서는 명령마다 저장된 규칙을 계산하거나 66으로 거부합니다.

v0.1.9의 Seal 0.1.36은 새 목표에 `run-rules/8`을 요구합니다. 그래서 `/8`을 지원하는 ha 0.1.9가 필요합니다.

Seal이 `--skill`로 가리킨 skill 폴더에 `core-requirements.json`이 있으면, `start`는 그 skill에 필요한 Core 지원을 실제 실행 파일과 대조합니다. 빠진 지원이 있으면 기록 없이 거부합니다. `--check-skill`을 함께 주면 그 선언이 필수입니다. 이 기능 전의 `ha`는 그런 시작을 받지 않습니다([Core 지원 정보 계약](../contracts/core-capabilities.md) §8).

> **Seal 0.1.26의 요구.** Seal 0.1.26은 새 목표에 `run-rules/6`을 요구했고 `ha start --rules run-rules/6 … --check-skill`로 시작했습니다. 형식과 기능 요구는 0.1.21과 같고 규칙만 바뀝니다. ha 0.1.8은 `/6`을 지원하지 않으므로 이 시작을 거부합니다. `/6`이나 다른 필수 지원이 없으면 Seal은 기록 없이 멈추고, 이전 규칙으로 물러나지 않습니다. 그 지원을 갖춘 `ha`가 필요합니다. 이미 시작한 `/1`~`/5` 목표는 저장된 규칙을 유지합니다.

Seal은 실제로 쓸 Core의 절대 경로를 정하고, 그 실행 파일의 `capabilities --format json`을 읽습니다. 새로 시작하려면 이해하는 기본 규칙과 필요한 지원이 모두 있어야 합니다. 기존 목표는 저장된 규칙과 요청한 동작을 기준으로 확인합니다.

다음 경우에는 기록 전에 멈추고 대상과 이유를 설명합니다.

- 조회를 지원하지 않거나 조회가 실패한 경우
- 조회한 정보가 잘못된 경우
- 기능이 부족한 경우

다른 실행 파일의 조회 결과를 재사용하지 않습니다. `/1`이나 `/2`로 바꿔 시작하지도 않습니다. 경로나 실행 파일 내용이 바뀌면 다시 확인합니다. 정확한 필드는 [Core 지원 정보 계약](../contracts/core-capabilities.md)에 있습니다.

이 지원 확인은 자동 설치, 권한 확대, 과거 기록 변경으로 우회하지 않습니다. 업데이트한 뒤에도 실제로 선택된 실행 파일의 지원 정보를 다시 읽습니다.

Python 호환 도우미는 선택 사항입니다. Python이 없어도 실제 지원 정보와 같은 계약을 직접 확인할 수 있습니다. Spec이 문서를 쓰는 데에는 Core나 이 조회가 필요 없습니다. 설치된 Codex·Claude 모델이 지침을 실제로 따르는지는 별도 호스트 평가의 대상입니다. 지원 정보 출력만으로는 이를 보증하지 않습니다.

### 예산과 도구

- 예산이 없으면 `검증 실행: 자동`으로 시작합니다. 승인이 필요할 때만 한 번 묻습니다.
- 검사에 필요한 도구는 baseline 전에 `ha doctor`로 점검합니다. 사용 불가인 도구는 한 질문으로 모아 묻습니다.

에이전트는 `ha estimate docs/specs/<goal>`로 PLAN의 최소 검증량과 상한을 비교할 수 있습니다. 예를 들어 `run-rules/6`까지는 필수 change가 34개면 최소 68회가 필요합니다. 조건마다 수정 전과 수정 후에 한 번씩 돌리기 때문입니다. manual과 review는 검사 실행 수에 들어가지 않습니다.

추정은 다음 양도 따로 표시합니다.

- 기본 비교 검증에 포함되는 선택 조건
- 명시적으로 고른 AC·EX·task 명령의 추가량

`--baseline`은 비교 검증으로 고른 양을 보여 줍니다. `--format json`은 기계가 읽는 출력을 냅니다.

PLAN에 `- 검증 실행: 자동`을 쓰면 `start`가 상한을 `max(50, ⌈필수 최소량 × 1.5⌉)`로 정합니다. 이 값은 사용자 설정 폴더의 `ha.json`에 적은 `preapproved_runs`와 비교합니다. 설정 폴더는 `~/.config/jaekit/`이고, `XDG_CONFIG_HOME`이 있으면 `$XDG_CONFIG_HOME/jaekit/`입니다.

- 그 값이 `preapproved_runs` 이하이면 묻지 않고 시작합니다. 파일이 없으면 그 상한은 50입니다.
- 넘으면 `start`가 `exceeds the pre-approved limit`로 기록 없이 멈춥니다. 그리고 사용자의 승인을 기다립니다.
- 파일을 쓸 수 없으면 `pre-approved run limit` 오류로 멈춥니다. 50으로 대신하지 않습니다.

형식과 예시는 [자동 예산](RULES.md#자동-예산)에 있습니다.

상한이 필수 최소량보다 작으면 `start`는 기록을 남기기 전에 거부합니다. 이때는 기존 허용 범위 안에서 목표를 나누거나, 시작 전에 충분한 예산을 정합니다. 추정치에는 재시도와 준비 시간이 들어 있지 않습니다. 진행 중인 목표에서 조회하면 현재 PLAN을 설명할 뿐입니다. 이미 기록된 상한이나 잔여량을 늘리지 않습니다.

### 커밋하지 않은 변경

검증 전에 `uncommitted changes`로 거부되면 출력된 경로를 확인합니다.

- `tracked`는 Git이 이미 관리하는 파일의 변경입니다. 작업 의도에 따라 commit하거나 되돌립니다.
- `untracked dependency symlink`는 링크 자체의 경로를 보고 보관할지 제외할지 판단합니다. 예를 들어 `apps/web/node_modules`가 표시되면 그 경로의 ignore 규칙을 검토합니다.

안내만으로 모든 `node_modules`를 제외하거나 파일을 자동으로 정리하지는 않습니다.

거부된 검사는 실행 횟수에 들어가지 않습니다. 여러 검사를 실행하다 멈췄다면, 앞서 실행한 결과와 사용량은 남습니다. 몇 개가 실행됐는지는 출력에서 알 수 있습니다. `ha status`의 `worktree_dirty`에도 경로와 유형이 나옵니다. Git 조회가 실패하면 깨끗한 상태로 취급하지 않습니다. 문제를 고친 뒤 검증을 다시 실행합니다.

### 목표 문서의 조건 형식

새 Spec 예시는 `Criteria-Format: nested/1`을 명시합니다. 이 표시가 있으면 AC 아래의 설명 목록을 같은 조건의 본문으로 읽습니다. 표시가 없는 기존 목표는 기존 해석을 유지합니다.

기존 목표에 이 표시를 추가하면 목표 문서가 바뀝니다. 그래서 이전 검증과 수동 확인을 새 해석에 재사용하지 않습니다. 들여쓰기 예시는 [목표 문서 계약](../contracts/goal-docs.md)에 있습니다.

## 수정 전 실패가 뜻하는 것

어떤 검사는 바꾸기 전에 **의도한 위반**을 보여야 합니다. `run-rules/6`까지는 모든 change 조건의 검사가, `run-rules/7`과 `run-rules/8`에서는 표시한 change 조건의 검사가 그렇습니다. 명령이 실패했다는 사실만으로는 수정 전 근거가 되지 않습니다.

change 검사는 선언한 대상과 요구 위반을 구조화 결과로 연결해야 합니다. 다음은 기대 실패로 인정하지 않습니다.

- 누락된 의존성
- import, 수집, 브라우저 기동 오류
- 실행하지 않았거나 skip된 검사
- 의미를 알 수 없는 스크립트 실패

실제로 실행한 검사가 기능이 없다는 것을 직접 관측한 결과는 이와 구분할 수 있습니다.

baseline을 기록할 때는 선언한 대상이 모두 실행돼야 합니다. 의도한 위반이 있어야 하고, 오류나 다른 assertion 실패가 없어야 합니다. baseline 요구 여부와 관계없이, 현재 검사는 선언한 대상이 모두 통과해야 합니다.

연결 방법은 [결과 계약과 참조 검사](../contracts/check-result.md)에 있습니다. 참조 검사는 파일을 실제로 읽는 작은 예시입니다. 특정 테스트 러너를 자동으로 설치하지 않고, 모든 러너를 지원하지도 않습니다.

### 이미 있는 시험에 연결하기

이미 있는 시험을 그대로 쓸 수도 있습니다. `ha capabilities`에 `check-adapter/v1`이 있는 Core에서는 [러너 어댑터](../contracts/check-result.md#5-runner-adapters)로 change 조건을 그 시험 하나에 연결합니다. 생산자 프로그램은 필요 없습니다. `ha`가 `go test -json …`의 출력이나, 러너가 `{HA_JUNIT_XML}` 위치에 쓴 JUnit XML을 직접 읽습니다.

성질이 깨졌을 때 나오는 assertion 실패 메시지의 첫 줄에 `jaekit:violation=<위반 식별자>` 표식을 넣습니다. 예를 들어 가상의 인사 CLI 시험이라면 `t.Fatalf("jaekit:violation=greeting-missing the CLI says %q", got)`처럼 씁니다.

표식이 없는 실패는 의도한 위반으로 인정하지 않습니다. 표식이 로그나 표준 출력에만 있어도 마찬가지입니다. 어댑터는 선택 사항입니다. 지원이 없으면 참조 검사나 전용 생산자를 씁니다.

### 오류와 재시도

`error`와 판정 불가는 함께 제한된 오류 재시도에 들어갑니다. 실제로 시도한 실패, 오류, stale와 그 사용량은 남습니다. 뒤에 통과해도, 같은 입력에서 나온 불리한 결과가 그것만으로 지워지지는 않습니다.

상태에 나온 이유와 해당 `ha log`를 봅니다. 그리고 검사, 제품, 환경 가운데 무엇이 달라져야 하는지 판단합니다.

<summary>규칙 버전(run-rules)별 차이</summary>

Seal 0.1.16부터 새 목표를 `run-rules/4`로 시작했습니다. 0.1.21부터는 `run-rules/5`로, 0.1.26부터는 `run-rules/6`으로 시작했습니다. v0.1.9의 Seal 0.1.36은 `run-rules/8`로 시작합니다.

`/5`는 `/4`를 모두 지키고, `standard`·`strict` 목표에 [검토 gate](RULES.md#검토-gate-run-rules5)를 더합니다. `/4`는 `/3`의 결과 규칙을 그대로 지키고, 오류 회복을 포함한 [자율 처리](RULES.md#자율-처리-run-rules4)를 더합니다.

Seal 0.1.26은 `run-rules/6`으로 시작합니다. `/6`은 `/5`의 판정 네 가지만 바꿉니다.

- `standard`·`strict` 목표에서 마지막 candidate 라운드(dry run 제외)가 시작 `base_commit`부터 검토하지 않았으면, `review_base_mismatch`로 완료를 막습니다. 시작 base부터의 candidate 뒤에 기록된 fixes 사슬은 Spar의 gate가 확인합니다.
- 완료 뒤 `review` note는 현재 등급이 `standard`·`strict`일 때만 완료 기록을 무효로 합니다. `light`이거나 등급 줄이 없으면, 다른 조건을 만족하는 완료 기록은 유효하게 남습니다.
- `record_head`가 앞선 줄의 hash이고, 그 줄과 `done` 줄 사이에 발견 줄(`run-finding/v1`)만 있거나 아무 줄도 없으면, 그 `done` 줄은 판정한 줄입니다. `record_head`가 가리키는 줄 자체는 발견 줄이어도 됩니다. 모든 `done` 줄은 전체 기록에서 먼저 판정합니다. 그래서 `record_head`가 판정하지 않은 줄을 가리켜도 판정한 줄이 될 수 있습니다. 그런 다음, 판정하지 않은 `done` 줄은 완료 여부와 관계없이 상태 계산에서 없는 것으로 취급합니다. 완료 기록과 그 설명, 최신 done 줄, 예산 창, 경과 시간, 완료 뒤 구간, 예산 변경 거부가 모두 이에 따릅니다. 상태, 보고, 비용, 예산 변경은 같은 뷰를 씁니다. 앞의 기록도 다른 유효성 조건을 만족해야 합니다. 판정했지만 다른 이유로 무효인 줄에서는 이전처럼 멈춥니다.
- 완료 뒤부터 다음 실행이나 완료가 아닌 `done`까지의 구간은 경과에서 뺍니다. 이 구간은 `post_completion_seconds`로 따로 보여 줍니다. 경계는 아래 예산 설명과 [계약 §4.9](../contracts/run-record.md#49-run-rules6)에 있습니다.

`/1`~`/5`로 시작한 기존 목표는 종전 판정을 유지합니다. 자동으로 이전되지 않습니다.

</details>

## baseline 선택과 검사 동결 (run-rules/7)

현재 Seal은 새 목표를 `run-rules/8`로 시작합니다. `/8`은 아래 baseline 선택을 그대로 두고, 검사 동결은 없습니다([실행 기록 계약](../contracts/run-record.md#411-run-rules8)). 지원하지 않는 Core에서는 기록 없이 멈추며, 이전 규칙으로 물러나지 않습니다. 직접 실행하는 `ha start`의 기본 규칙은 그대로 `run-rules/3`입니다. 이미 `/1`~`/7`로 시작한 목표의 판정, 출력, 기록은 바뀌지 않습니다.

PLAN 조건표의 선택 `baseline` 열에 `요구`를 적은 change 조건만 baseline을 요구합니다. 빈 칸이나 `—`, 또는 열이 없으면 요구하지 않습니다. Seal은 두 가지에만 표시합니다.

- base commit에 이미 있는 결함을 고치는 버그 수정·회귀
- "X가 일어나지 않는다" 같은 금지 조건

새 기능을 더하는 조건은 기본으로 표시하지 않습니다. 표시한 조건마다 plan 라운드 전에 REVIEW에 이유를 적습니다. 표시하지 않은 조건에는 이유가 필요 없습니다. 이미 시작한 목표는 시작할 때의 표시를 그대로 둡니다. 표시하지 않은 change 조건에도 검사 경로와 구조화 결과 계약은 필요합니다. 다만 base에도 있는 진입점에 묶을 필요는 없고, 새 함수의 시험에 연결할 수 있습니다.

필수 최소량은 `표시한 필수 change × 2 + 표시하지 않은 필수 change + 필수 maintain`입니다. manual과 review는 0회입니다. 표시한 change 1개, 표시하지 않은 change 4개, maintain 3개가 모두 필수라면 최소 9회입니다. 이때 자동 상한은 `max(50, ⌈9 × 1.5⌉) = 50`입니다. 시작 전에는 `ha estimate <goal> --rules run-rules/8`로 이 값을 봅니다. 시작한 목표는 저장된 규칙을 쓰며, 다른 `--rules`를 주면 거절합니다.

대상 없는 `ha check <goal> --baseline`은 표시한 change 조건만 고릅니다. 표시한 선택 조건도 여기에 들어갑니다. 표시가 하나도 없으면 기록 없이 거절합니다. 표시하지 않은 조건을 직접 지정해 baseline을 실행할 수도 있습니다. 그 실제 실행은 예산에 셉니다. 그 baseline의 신선한 불리한 결과도 판정에 남습니다.

표시한 조건의 baseline은 마지막 검토 라운드 뒤, 완료 기록 직전에 한 번 기록합니다. 그 baseline이 선언한 위반 대신 통과하거나 오류를 내면 Seal은 검사를 고칩니다. 고친 검사는 고친 코드처럼 검토받고, 그 뒤 baseline을 다시 기록합니다. 이 안내는 검사를 고칠 때마다 기록하는 습관을 줄이려는 것입니다. 이미 낡은 근거를 신선하게 만드는 예외가 아닙니다.

`/7`과 `/8`에서는 "baseline 전" 질문 모으기, `ha doctor`, `strict`의 plan 라운드를 첫 `ha check` 기록 전에 마칩니다. 그 기록이 현재 검사이든 baseline이든 같고, baseline이 없는 목표에서도 같습니다. 시작 전에 알 수 있는 질문을 모으되, 물을 것이 없으면 바로 일합니다.

입력 실패는 다음처럼 다룹니다.

- 입력 실패인 대상 파일 없음, 손상된 입력, 시작하지 못하는 도구, 신호 종료는 통과가 아닙니다.
- baseline을 요구하지 않는 검사(maintain, `EX-n`, task 명령, 표시하지 않은 change 조건)는 입력 실패를 위반, 오류, 판정 불가 중 하나로 셀 수 있습니다. 그것만으로 검사의 결함이 되지는 않습니다. 위반으로 기록된 실패는 입력이 달라질 때까지 남습니다.
- baseline을 요구하는 change 조건의 전용 생산자는 입력 실패를 위반으로 보고하지 않습니다. 결과 계약이 허용하는 경우(예: `missing: violation`)는 예외입니다. 그 선택은 plan 라운드 전에 `REVIEW.md`에 적습니다. plan 라운드가 없으면 어떤 검토 라운드보다도 전에 적습니다.

baseline을 요구하는지는 규칙에 따라 읽습니다. `run-rules/6`까지는 모든 change 조건이 요구하고, `/7`과 `/8`은 표시한 조건만 요구합니다. 러너 어댑터는 입력 실패를 스스로 분류합니다. [결과 계약](../contracts/check-result.md)의 분류와 입력 실패 표는 바뀌지 않습니다.

**`run-rules/7`의 검사 동결.** 동결 시점은 기록된 마지막 gate의 dry run이 아닌 라운드 가운데, `strict`이면 첫 `plan` 라운드, `standard`이면 첫 `candidate` 라운드입니다. 동결 대상은 조건표에서 검사 경로를 적은 모든 행의 경로에 있는 선언, 생산자, 시험, 도우미, 설정입니다. Seal은 동결 라운드 바로 뒤에 `ha note <goal> review --gate <file>`로 gate와 그때 조건표의 검사 경로를 기록합니다. 동결 라운드에서 끝난 gate note가 없으면 뺀 검사 경로를 관측할 수 없습니다. 그러면 상태와 보고에 `동결 때의 조건표가 기록되지 않음`이 나옵니다.

동결 뒤 검사 파일을 고치면 commit하고, `ha note <goal> check-change checks:<path> --reason "<지적 ID, 또는 조건과 이유>"`로 까닭을 남깁니다. 검토 지적을 고친 변경이면 그 지적 ID를 씁니다. 까닭은 지금 blob에 묶입니다. 그래서 파일을 다시 바꾸면 그 변경의 까닭도 다시 남깁니다. 다음 candidate 라운드에 바뀐 검사와 까닭을 함께 주면, 그 라운드가 바뀐 검사를 검토합니다. 동결 전 변경에는 이 까닭이 필요 없습니다. 동결 뒤에도 검사 결함을 고칠 수 있습니다. 동결 표시는 그 자체로 완료를 막지 않습니다.

`ha status`는 change 조건마다 `baseline_required`와 사람용 `baseline required` 줄을 보여 줍니다. `ha report`의 `확인한 것`은 모든 change 조건 중 baseline을 요구한 수와, 그중 신선한 baseline이 있는 수를 나눠 보여 줍니다. `직접 볼 것`에서는 시작 뒤 뺀 baseline 표시, 동결 뒤 바뀐 검사 파일과 까닭, 까닭 없는 변경을 읽습니다. 뺀 경로에는 비교에 쓴 `review` note seq가 붙습니다. `light` 목표와 기록된 gate가 없는 목표에는 동결 표시가 없습니다. 검수 요약의 `### 보지 않은 것`에는 baseline 없이 충족한 change 조건을 적습니다. 정확한 필드와 표시는 [실행 기록 계약 §4.10](../contracts/run-record.md#410-run-rules7)에 있습니다.

## 완료 보고 읽기

완료 보고는 목표 폴더의 `PROGRESS.md`와 대화에 함께 나옵니다. 다음을 확인합니다.

1. **무엇이 바뀌었는가.** 실제 파일, 화면, 동작이 요청과 맞는지 봅니다.
2. **필수 조건이 어떻게 충족됐는가.** 자동 검사 결과, 직접 확인한 항목, 검토 gate로 충족한 `review` 조건을 구분합니다. `review` 조건은 `직접 볼 것`에 gate 기록의 seq와 함께 나옵니다. 선택 조건은 완료를 막지 않으며 따로 표시합니다.
3. **검사가 무엇을 다뤘는가.** 새 동작을 확인한 검사, 유지해야 할 동작, 확인하지 못한 범위를 봅니다. 검증 명령이나 조건 종류를 바꿨다면 이유를 확인합니다.
4. **가정과 한계가 무엇인가.** 에이전트가 정한 가정이 의도와 맞는지 봅니다. 남은 한계가 결과에 영향을 주는지도 봅니다.

완료의 근거는 `ha done`이 남긴 완료 기록입니다. 터미널에서 `ha status <goal>`을 실행하면 현재 목표와 기록에 따른 상태를 볼 수 있습니다. `<goal>`은 `docs/specs/login-link`처럼 실제 목표 폴더 경로로 바꿉니다.

Seal 0.1.20 이상으로 시작한 목표의 완료 보고에는 `ha report`의 출력이 그대로 붙습니다. 맨 위 다섯 줄을 먼저 읽고, 그 아래에서 완료 기록과 Seal의 판단 문장을 봅니다. 0.1.24 이상으로 시작해 완료한 목표에서는 판단 문장이 `## 검수 요약`에 있습니다. `ha report <goal> --lang ko`는 같은 기록을 `바뀐 것`, `확인한 것`, `직접 볼 것`, `남은 한계`, `다음 행동` 다섯 줄로 요약합니다. `ha status`와 같은 계산이며 기록을 바꾸지 않습니다. 요약 아래의 도장은 `PROGRESS.md`의 `## 현재`가 어느 기록 head를 기준으로 쓰였는지 맞춰 볼 때 씁니다.

**검수 요약.** Seal 0.1.24 이상으로 시작한 목표에서는, 완료 기록 뒤 `## 현재` 바로 다음의 `## 검수 요약`에서 검수를 시작합니다. 맨 위 줄에는 완료 기록, 보증 등급, 충족한 필수 조건 수, 검토 gate 결과, 이 변경이 하는 일, 먼저 볼 것이 있습니다. 그 아래에 바뀐 것, 근거, 직접 볼 것, 보지 않은 것이 이 순서로 옵니다. 해당하는 것이 없는 항목에는 `없음`을 씁니다. 목표를 다시 열어 완료를 다시 기록하면, 새 완료 기록을 기준으로 다시 씁니다.

이 절은 사용자의 언어로 씁니다. 기록은 그것이 무엇인지를 먼저 쓰고, 항목마다 짧게 씁니다. seq는 보조로만 붙입니다. 검증 출력과 지적 원문은 옮기지 않습니다. 지적은 ID, 한 줄 요약, 끝만 적습니다. Seal의 판단은 이 절에만 있습니다. `## 완료 보고`에는 `ha report` 출력과 이 절을 가리키는 한 줄이 있습니다. 완료한 목표는 `## 검수 요약`부터 읽습니다. 멈춘 목표와 그 전 Seal로 시작한 목표는 지금처럼 `## 완료 보고`를 읽습니다.

보증 수준 `local`은 그 컴퓨터에서 얻은 근거라는 뜻입니다. 검사는 실행한 에이전트가 작성합니다. 그 에이전트는 같은 사용자 권한으로 파일과 기록을 바꿀 수 있습니다. `local`은 결과 전체에 결함이 없다는 뜻도, 독립된 제3자의 보증도 아닙니다.

빠진 것이 있으면 무엇을 고칠지 말합니다. 그러면 Seal이 사용자 요청을 인용한 `reopen`을 기록하고 재작업합니다. 이전 완료 기록은 현재 완료 근거로 쓰이지 않고, 새 예산 창이 열립니다. 목표 문서부터 바꿔야 한다면 Spec으로 고친 뒤 계속하라고 따로 요청합니다.

검사 출력 원문이 필요하면 터미널에서 `ha log <goal> <seq>`로 봅니다. `<seq>`는 보고에 나온 기록 번호입니다. 실행 뒤 출력 저장이 실패한 `process_output` 기록은 원문 경로가 비어 있을 수 있습니다. 그래도 실제 시도와 사용량은 남습니다. 기록 저장 오류로 적용 여부가 불확실하면 성공으로 단정하지 말고 저장 상태를 확인합니다. 보존된 원문은 해당 작업 트리의 Git 디렉토리 아래 `ha/`에 있으며, Git이 추적하지 않습니다([저장되는 파일](USAGE.md#저장되는-파일)).

## `needs_user` 처리

에이전트가 정할 수 없는 항목이 남으면 이유와 함께 묻습니다. 필요한 판단을 하고 답하면 그 답이 기록됩니다.

| 이유 | 확인할 것 | 이어 가는 방법 |
| --- | --- | --- |
| `manual_unconfirmed` | 자동 검사로 확인할 수 없는 조건을 직접 확인했는가 | 결과를 확인한 뒤 알려 줍니다. 조건 문장이 바뀌면 다시 확인해야 합니다 |
| `review_tier_missing` | 검토 등급이 `light`이거나 없는 목표에 `review` 조건이 있는가. `review`는 제품 동작이 읽지 않는 문서 내용에 관한 조건입니다. `standard`·`strict` 목표의 독립 검토 gate로만 충족됩니다 | Spec으로 목표 문서의 `Assurance:` 등급을 `standard`나 `strict`로 올리거나 그 기준을 고칩니다 |
| `out_of_scope` | 계획 범위 밖의 변경이 필요한가 | 해당 변경을 허용하거나 되돌리게 합니다. 목표 자체가 바뀌면 Spec으로 고칩니다 |
| `test_definition_changed` | 기존 테스트 변경이 정당한가 | 변경 이유와 내용을 보고 허용하거나 되돌리게 합니다 |
| `spec_changed` | 목표 문서 변경이 의도한 것인가 | 의도한 변경이면 확인합니다. 고친 뒤 보낸 계속·구현 요청도 확인으로 기록됩니다 |
| `error_limit` | 같은 코드에서 검사 오류가 반복된 원인이 무엇인가 | 환경을 고친 뒤 다시 실행하게 합니다. 직접 확인할 조건으로 바꾸려면 먼저 목표를 검토합니다 |
| `record_integrity` | 실행 기록이 손상됐는가 | 원인을 확인합니다. 기록을 임의로 고쳐 통과시키지 말고, 필요하면 새 목표 폴더에서 시작합니다 |
| `review_open_question` | 기록된 검토 gate에 남은 `requirement-question`이 무엇을 묻는가 | 질문에 답합니다. 에이전트가 답을 기록하고 검토를 다시 받아 새 gate를 기록합니다([검토 gate](RULES.md#검토-gate-run-rules5)) |

`review_pending`은 이 표에 없습니다. 사용자가 아니라 에이전트가 해소하기 때문입니다. 이 이유는 `review` 조건에 대해 검토 gate가 아직 지금 HEAD와 목표 문서를 덮지 않았거나, 다른 검토 이유가 남았다는 뜻입니다. 에이전트가 남은 검토 라운드를 돌리고 gate를 기록합니다.

## 막힘과 예산

- **`blocked`**: 인증 만료, 권한 거부, 사용량 한도 등으로 멈춘 상태입니다. 에이전트가 남긴 해소 조건을 읽고 원인을 해결한 뒤, 계속하라고 말합니다.
- **`budget_exhausted`**: 검사 횟수의 예산을 넘었거나, `run-rules/7`까지는 경과 시간의 예산을 넘은 상태입니다. 남은 일과 어떤 한도를 넘었는지 보고 더 쓸지 정합니다.

`/4` 이상은 아래 `/3`의 예산 규칙을 따릅니다. 그러면서 신고한 대기와 재개한 창의 상한을 따로 정합니다. `run-rules/7`까지는 사전 승인한 상한도 따로 정합니다. 그 차이는 [자율 처리](RULES.md#자율-처리-run-rules4)와 [실행 기록 계약](../contracts/run-record.md#47-run-rules4)을 봅니다. `run-rules/6`은 완료 뒤 시간도 아래처럼 뺍니다.

`/3`에서 횟수만 더 쓰려면 현재 창의 총상한을 변경합니다.

- 사용량 48회·상한 50회에서 상한을 100회로 바꾸면 사용량 48회·잔여 52회입니다.
- 40회로 줄이면 잔여 0회·초과 8회입니다. 쓴 기록은 사라지지 않습니다.
- 증액에는 그 한도를 허용한 사용자 원문과 요청 문맥이 남습니다. 감액에는 이유가 남습니다.
- 짧은 “좋아”도 무엇에 동의했는지 문맥이 있으면, 형식만으로 거부하지 않습니다.
- 인용 출처를 확인하지 못했다면, 그것은 에이전트가 기록한 주장입니다.

변경은 상태의 창 번호, 예산 개정, 현재 상한에 연결됩니다. 그래서 다른 변경이나 재개와 충돌하면 자동으로 덮어쓰거나 합산하지 않습니다. 현재 상태를 다시 확인해 결정합니다. 저장 오류가 적용 여부의 불확실성을 알리면, 다시 적용하기 전에 기록을 확인합니다. [정확한 명령과 필드](../contracts/run-record.md#52-budget)는 제품 계약에 있습니다.

이 변경은 새 창을 열지 않습니다. 시간 상한, 경과 시간, 실패·오류 한도, 막힘도 초기화하지 않습니다. 시간 상한 변경은 지원하지 않습니다. PLAN을 고치는 것만으로는 진행 중인 상한이 바뀌지 않습니다. 완료된 창에는 명시적인 재작업이나 재개가 필요합니다. `/3`의 새 창은 최신 횟수 상한과 기존 시간 상한을 이어받습니다.

> `/1`·`/2` 목표는 기존처럼 사용자 발화를 인용한 `reopen`으로 최초 상한의 새 창을 엽니다.

예산 창은 마지막 시작이나 `reopen`부터, 실행 예산 대상인 마지막 기록의 시각까지입니다. 발견 줄은 예산 입력에서 빠집니다. 상태를 조회하는 것만으로 시간이 늘지는 않습니다. 하지만 예산 변경을 포함해 새 기록이 붙으면 창이 늘어납니다. `/4`·`/5`는 창 길이에서 신고한 대기를 뺍니다. `run-rules/6`은 완료 뒤 구간도 뺍니다. 재개를 걸쳐 실행한 검사는 기록된 창에서 계산합니다. 검사·baseline의 실제 시도, 오류·판정 불가, 유효·stale는 서로 다른 집계 축입니다. baseline도 사용량에 들어갑니다.

**완료 뒤 구간(`run-rules/6`).** 이 구간은 판정한 `complete` `done`의 `at`에서 시작합니다. 끝은 다음 두 시점 가운데 이른 쪽입니다.

- 그 `at`과 같은 초나 그 뒤에 시작한 검사·baseline 가운데 가장 이른 `started_at`
- 완료가 아닌 `done`의 `at`

완료 전에 시작해 그 뒤 기록된 실행은 구간을 끝내지 않습니다. 두 시점이 모두 없으면 창의 마지막 예산 기록에서 끝납니다. 다른 완료 `done`은 구간을 이어 갑니다. note와 발견 줄은 구간을 끝내지 않습니다. 실행 구간은 경과에 남고, 신고 대기와 겹친 시간은 한 번만 빠집니다. 추가로 뺀 초가 `budget.post_completion_seconds`이며, `elapsed_seconds = span_seconds - reported_wait_seconds - post_completion_seconds`입니다. 사람용 상태의 Budget 절과 `ha cost` JSON의 예산 창도 이 초를 따로 보여 줍니다. `ha report`의 남은 한계와 `ha cost`는 같은 경과를 씁니다. 완료 뒤 첫 실행 전의 작업 시간도 빠집니다. 그래서 코드 재작업은 사용자 요청을 인용한 `reopen`으로 새 창에서 진행합니다. 실행 횟수와 상한, 완료 창의 예산 변경 거부는 그대로입니다.

도달은 사용량과 상한이 같은 경우이고, 초과는 실제로 넘은 경우입니다. 완료 기록이 있는 목표는 시간이 지나도 예산 초과 상태가 되지 않습니다. `/2`~`/8`에서는 필수 조건이 모두 충족되고 예산 초과만 남았으면 완료를 기록할 수 있습니다. 이것은 추가 실행 권한이 아닙니다. 예산은 검사 실행을 자동으로 막거나 진행 중인 검사를 끝내는 장치도 아닙니다.

## 새 대화에서 이어 가기

같은 프로젝트 폴더에서 새 대화를 열고 `docs/specs/<goal> 이어서 해줘`라고 보냅니다. Seal이 목표, 계획, 진행 기록과 현재 상태를 읽고 남은 일을 이어 갑니다. 사용자 판단이 필요한 항목이 남아 있으면 먼저 답합니다.

## 검증 근거 보고

Seal 0.1.10부터 도입된 보고 형식은 기대 결과의 근거, 실제 관측 경계, 시험 방법과 대체 환경을 구분합니다. 같은 근거는 조건 그룹으로 참조할 수 있습니다. 검토에는 예정을 남깁니다. 완료·중단 보고에는 실제 결과와 미관측·남은 위험을 남깁니다. 실제 실행은 그 자체로 정답의 근거가 아닙니다. fake 결과가 실제 모델 관측으로 바뀌지도 않습니다. 시각 출처와, 판단을 바꾼 새 사실도 구별합니다.

기존 목표는 시작 형식을 유지합니다. 누락된 새 항목은 미기록입니다. 과거 완료를 덮어쓰거나 관측을 채우지 않습니다. 이 보고 형식은 Seal 0.1.12부터 포함되며, 현재 배포판 v0.1.9에도 들어 있습니다. [가상 보고 예시](../examples/verification-reporting.md)를 참고하세요.

## 보증 정책

필요한 독립 검토나 실제 경계 근거가 없으면 완료 보류합니다. 무관한 작업은 계속할 수 있습니다.

Seal 0.1.20부터는 SPEC의 `Assurance:` 등급이 독립 검토 단계를 정합니다.

- `standard`는 최종 후보의 candidate 라운드와, 검토 수정 뒤 base commit부터의 candidate 라운드를 받습니다. 마지막 candidate 라운드가 누적 라운드입니다.
- `strict`는 여기에 baseline 전 plan 라운드 한 번을 더합니다.
- `light`는 이유를 남기고 생략할 수 있습니다.
- 프로젝트 지침이 더 많은 검토를 요구하면 그쪽을 따릅니다.

독립 검토가 필요한 목표는 마지막 head 전체를 본 누적 라운드가 열린 지적 없이 끝난 뒤에만 `ha done`을 실행합니다([사용 안내](USAGE.md#seal의-시작-전-확인과-검토-순서)).

## 완료 뒤 발견 문서

Seal 0.1.12의 새 보고 형식은 당시 완료 보고를 보존합니다. 그리고 이후 발견의 대상 버전, 조건, 재현 범위, 판단 이력, 재작업 요청을 연결합니다. 미해결 발견과 역사적 완료는 동시에 표시할 수 있습니다. 문서 상태가 Core의 구조화 조회나 동시 변경 처리를 대신하지는 않습니다. 발견 기록만으로 실행이 재개되거나 예산이 바뀌지도 않습니다. [가상 발견 이력](../examples/verification-findings.md)은 실제 실행 기록이 아닙니다.
