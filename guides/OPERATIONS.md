# 작업 상태와 완료 보고 읽기

이 문서는 v0.1.3(ha 0.1.3·spec 0.1.11·seal 0.1.9)의 실행 전 진단·지원 확인, `nested/1`, `/3` 결과와 횟수 총상한 변경을 설명합니다. 기존 목표는 저장된 규칙과 형식을 유지합니다. 배포판과 소스 빌드의 차이는 [버전별 적용 범위](INSTALL.md#배포판과-개발-조합)에 있습니다.

처음 쓰는 사람을 위한 호출·재개·문제 해결은 [사용 안내](USAGE.md)에 있습니다([English](USAGE.en.md)). 설치와 버전 확인은 [설치 안내](INSTALL.md)를 봅니다. 이 문서는 작업 중 질문과 완료 보고를 더 자세히 읽는 방법을 설명합니다.

## 목표 맡기기

Spec은 요청을 `docs/specs/<goal>/SPEC.md`에 목표·범위·완료 조건으로 정리하고 보고한 뒤 멈춥니다. 결과를 바꾸는 질문에 답하거나 고칠 것을 말해 목표를 다듬습니다. `Status: Ready`는 문서가 준비됐다는 표시이며 구현을 시작하지는 않습니다.

준비되면 Codex 대화에서 `$` 목록의 `seal:seal`을 골라 별도 메시지로 `$seal:seal docs/specs/<goal>`을 보냅니다. Claude Code에서는 `/seal:seal docs/specs/<goal>`을 씁니다. 이미 목표 문서가 있다면 바로 Seal에 맡겨도 됩니다. 에이전트가 계획·검사 방법을 검토하고 구현·검사·수정을 이어 갑니다. 매 작업마다 승인할 필요는 없습니다.

목표와 범위를 바꿀지는 사용자가 정합니다. Seal은 목표 문서를 고치지 않습니다. Spec으로 목표를 고쳤다면 별도로 `docs/specs/<goal> 이어서 해줘`라고 요청합니다. 자세한 문서 형식은 [목표 문서 계약](../contracts/goal-docs.md)과 [실행 묶음 계약](../contracts/bundle.md)에 있습니다.

## 실행 전에 확인할 것

Seal은 실제 사용할 Core의 절대 경로를 정하고 그 실행 파일의 `capabilities --format json`을 읽습니다. 새 시작은 이해하는 기본 규칙과 필요한 지원이 모두 있어야 하며, 기존 목표는 저장된 규칙과 요청한 동작을 기준으로 확인합니다. 조회 미지원·실패·잘못된 정보·부족한 기능이면 기록 전에 멈추고 대상과 이유를 설명합니다. 다른 실행 파일의 조회 결과를 재사용하거나 `/1`·`/2`로 바꿔 시작하지 않습니다. 경로나 실행 파일 내용이 바뀌면 다시 확인합니다. 정확한 필드는 [Core 지원 정보 계약](../contracts/core-capabilities.md)에 있습니다.

이 지원 확인은 자동 설치·권한 확대·과거 기록 변경으로 우회하지 않습니다. 업데이트 뒤에도 실제 선택된 실행 파일의 지원 정보를 다시 읽습니다. Python 호환 도우미는 선택 사항이며, Python이 없어도 실제 지원 정보와 같은 계약을 직접 확인할 수 있습니다. Spec의 문서 작성에는 Core나 이 조회가 필요 없습니다. 설치된 Codex·Claude 모델이 지침을 실제로 따르는지는 별도 호스트 평가 대상이며, 지원 정보 출력만으로 보증하지 않습니다.

에이전트는 `ha estimate docs/specs/<goal>`로 PLAN의 최소 검증량과 상한을 비교할 수 있습니다. 예를 들어 필수 change가 34개면 수정 전·후 각 한 번씩 최소 68회가 필요합니다. manual은 검사 실행 수에 포함되지 않습니다. 기본 비교 검증에 포함되는 선택 조건과 명시적으로 선택한 AC·EX·task 명령의 추가량도 따로 표시합니다. `--baseline`은 비교 검증 선택량을, `--format json`은 기계가 읽는 출력을 제공합니다.

상한이 필수 최소량보다 작으면 `start`는 기록을 남기기 전에 거부합니다. 기존 허용 범위에서 목표를 나누거나 시작 전에 충분한 예산을 결정합니다. 추정치에는 재시도와 준비 시간이 들어 있지 않습니다. 진행 중 목표에서 조회하면 현재 PLAN을 설명할 뿐이며 이미 기록된 상한이나 잔여량을 늘리지 않습니다.

검증 전에 `uncommitted changes`로 거부되면 출력된 경로를 확인합니다. tracked는 Git이 이미 관리하는 파일의 변경이므로 작업 의도에 따라 commit하거나 되돌립니다. untracked dependency symlink는 링크 자체의 경로를 보고 보관·제외 여부를 판단합니다. 예를 들어 `apps/web/node_modules`가 표시되면 그 경로의 ignore 규칙을 검토합니다. 안내만으로 모든 `node_modules`를 제외하거나 파일을 자동 정리하지는 않습니다.

거부된 검사는 실행 횟수에 들어가지 않습니다. 여러 검사를 실행하다 멈췄다면 앞서 실행한 결과와 사용량은 남으며 출력에서 몇 개가 실행됐는지 알 수 있습니다. `ha status`의 `worktree_dirty`에도 경로와 유형이 나옵니다. Git 조회 실패는 깨끗한 상태로 취급하지 않습니다. 문제를 고친 뒤 검증을 다시 실행합니다.

새 Spec 예시는 `Criteria-Format: nested/1`을 명시해 AC 아래의 설명 목록을 같은 조건의 본문으로 읽습니다. 표시가 없는 기존 목표는 기존 해석을 유지합니다. 기존 목표에서 표시를 추가하면 목표 문서가 변경되므로 이전 검증과 수동 확인을 새 해석에 재사용하지 않습니다. 들여쓰기 예시는 [목표 문서 계약](../contracts/goal-docs.md)을 참고합니다.

## 수정 전 실패가 뜻하는 것

새 목표는 `run-rules/3`으로 시작합니다. change 검사는 선언한 대상과 요구 위반을 구조화 결과로 연결해야 합니다. 명령이 실패했다는 사실만으로 수정 전 근거가 되지는 않습니다. 누락된 의존성, import·수집·브라우저 기동 오류, 미실행·skip, 의미를 알 수 없는 스크립트 실패는 기대 실패로 인정하지 않습니다. 실제 실행한 검사가 기능 부재를 직접 관측한 결과는 구분할 수 있습니다.

선언한 모든 대상이 실행돼야 하며, 수정 전에는 의도한 위반이 있고 오류나 다른 assertion 실패가 없어야 합니다. 현재 검사는 같은 대상 전체의 통과가 필요합니다. [결과 계약과 참조 검사](../contracts/check-result.md)에 연결 방법이 있습니다. 참조 검사는 파일을 실제로 읽는 작은 예시이며 특정 테스트 러너를 자동 설치하거나 모든 러너를 지원하지 않습니다.

`error`와 판정 불가는 제한된 오류 재시도에 함께 포함됩니다. 실제 시도한 실패·오류·stale와 사용량은 남습니다. 뒤의 통과만으로 같은 입력에서 나온 불리한 결과를 지우지 않습니다. 상태에 나온 이유와 해당 `ha log`를 보고 검사·제품·환경 중 무엇이 달라져야 하는지 판단합니다. `/1`·`/2`로 시작한 기존 목표는 종전 분류를 유지하며 자동 이전되지 않습니다.

## 완료 보고 읽기

완료 보고는 목표 폴더의 `PROGRESS.md`와 대화에 함께 나옵니다. 다음을 확인합니다.

1. **무엇이 바뀌었는가.** 실제 파일·화면·동작이 요청과 맞는지 봅니다.
2. **필수 조건이 어떻게 충족됐는가.** 자동 검사 결과와 직접 확인한 항목을 구분합니다. 선택 조건은 완료를 막지 않으며 따로 표시합니다.
3. **검사가 무엇을 다뤘는가.** 새 동작을 확인한 검사, 유지해야 할 동작, 확인하지 못한 범위를 봅니다. 검증 명령이나 조건 종류를 바꿨다면 이유를 확인합니다.
4. **가정과 한계가 무엇인가.** 에이전트가 정한 가정이 의도와 맞는지, 남은 한계가 결과에 영향을 주는지 봅니다.

완료의 근거는 `ha done`이 남긴 완료 기록입니다. 터미널에서 `ha status <goal>`로 현재 목표와 기록에 따른 상태를 확인할 수 있습니다. `<goal>`은 `docs/specs/login-link`처럼 실제 목표 폴더 경로로 바꿉니다.

보증 수준 `local`은 해당 컴퓨터에서 얻은 근거라는 뜻입니다. 검사는 실행한 에이전트가 작성하며 같은 사용자 권한으로 파일과 기록을 바꿀 수 있습니다. 결과 전체의 무결함이나 독립된 제3자의 보증을 뜻하지 않습니다.

빠진 것이 있으면 무엇을 고칠지 말합니다. Seal이 사용자 요청을 인용한 `reopen`을 기록하고 재작업합니다. 이전 완료 기록은 현재 완료 근거로 쓰이지 않으며 새 예산 창이 열립니다. 목표 문서부터 바꿔야 한다면 Spec으로 고친 뒤 별도로 계속하라고 요청합니다.

검사 출력 원문이 필요하면 터미널에서 `ha log <goal> <seq>`로 봅니다. `<seq>`는 보고에 나온 기록 번호입니다. 실행 뒤 출력 저장이 실패한 `process_output` 기록은 실제 시도와 사용량이 남아도 원문 경로가 비어 있을 수 있습니다. 기록 저장 오류로 적용 여부가 불확실하다면 성공으로 단정하지 않고 저장 상태를 확인합니다. 보존된 원문은 해당 작업 트리의 Git 디렉토리 아래 `ha/`에 있고 Git이 추적하지 않습니다([저장되는 파일](USAGE.md#저장되는-파일)).

## `needs_user` 처리

에이전트가 정할 수 없는 항목이 남으면 이유와 함께 묻습니다. 필요한 판단을 하고 답하면 그 답이 기록됩니다.

| 이유 | 확인할 것 | 이어 가는 방법 |
| --- | --- | --- |
| `manual_unconfirmed` | 자동 검사로 확인할 수 없는 조건을 직접 확인했는가 | 결과를 확인한 뒤 알려 줍니다. 조건 문장이 바뀌면 다시 확인해야 합니다 |
| `out_of_scope` | 계획 범위 밖의 변경이 필요한가 | 해당 변경을 허용하거나 되돌리게 합니다. 목표 자체가 바뀌면 Spec으로 고칩니다 |
| `test_definition_changed` | 기존 테스트 변경이 정당한가 | 변경 이유와 내용을 보고 허용하거나 되돌리게 합니다 |
| `spec_changed` | 목표 문서 변경이 의도한 것인가 | 의도한 변경이면 확인합니다. 고친 뒤 보낸 계속·구현 요청도 확인으로 기록됩니다 |
| `error_limit` | 같은 코드에서 검사 오류가 반복된 원인이 무엇인가 | 환경을 고친 뒤 다시 실행하게 합니다. 직접 확인할 조건으로 바꾸려면 먼저 목표를 검토합니다 |
| `record_integrity` | 실행 기록이 손상됐는가 | 원인을 확인합니다. 기록을 임의로 고쳐 통과시키지 말고, 필요하면 새 목표 폴더에서 시작합니다 |

## 막힘과 예산

- **`blocked`**: 인증 만료, 권한 거부, 사용량 한도 등으로 멈춘 상태입니다. 에이전트가 남긴 해소 조건을 읽고 원인을 해결한 뒤 계속하라고 합니다.
- **`budget_exhausted`**: 검사 횟수나 경과 시간의 예산을 넘은 상태입니다. 남은 일과 어떤 한도를 넘었는지 보고 더 쓸지 정합니다.

`/3`에서 횟수만 더 쓰려면 현재 창의 총상한을 변경합니다. 사용량 48회·상한 50회에서 상한을 100회로 바꾸면 사용량 48회·잔여 52회입니다. 40회로 줄이면 잔여 0회·초과 8회이며 쓴 기록은 사라지지 않습니다. 증액에는 그 한도를 허용한 사용자 원문과 요청 문맥, 감액에는 이유가 남습니다. 짧은 “좋아”도 무엇에 동의했는지 문맥이 있으면 형식만으로 거부하지 않습니다. 인용 출처를 확인하지 못했다면 에이전트가 기록한 주장입니다.

상태의 창 번호·예산 개정·현재 상한에 연결해 변경하므로 다른 변경이나 재개와 충돌하면 자동으로 덮어쓰거나 합산하지 않습니다. 현재 상태를 다시 확인해 결정합니다. 저장 오류가 적용 불확실성을 알리면 다시 적용하기 전에 기록을 확인합니다. [정확한 명령과 필드](../contracts/run-record.md#52-예산)는 제품 계약에 있습니다.

이 변경은 새 창을 열지 않고 시간 상한·경과 시간·실패·오류 한도·막힘을 초기화하지 않습니다. 시간 상한 변경은 지원하지 않습니다. PLAN을 고치는 것만으로 진행 중 상한은 바뀌지 않습니다. 완료된 창은 명시적 재작업·재개가 필요하며 `/3`의 새 창은 최신 횟수 상한과 기존 시간 상한을 이어받습니다. `/1`·`/2`는 기존처럼 사용자 발화를 인용한 `reopen`으로 최초 상한의 새 창을 엽니다.

예산은 마지막 시작이나 `reopen`부터 마지막 저장 기록 시각으로 잽니다. 상태 조회만으로 시간이 늘지는 않지만 예산 변경을 포함한 새 기록이 붙으면 기다린 시간도 들어갑니다. 재개를 걸쳐 실행한 검사는 기록된 창에 계산됩니다. 검사·baseline의 실제 시도, 오류·판정 불가, 유효·stale는 서로 다른 집계 축입니다. baseline도 사용량에 포함됩니다.

도달은 사용량과 상한이 같은 경우이고 초과는 실제로 넘은 경우입니다. 완료 기록이 있는 목표는 시간이 지나도 예산 초과 상태가 되지 않습니다. `/2`·`/3`는 필수 조건이 모두 충족되고 예산 초과만 남았으면 완료를 기록할 수 있습니다. 이는 추가 실행 권한이 아니며 예산은 검사 실행을 자동 차단하거나 진행 중 검사를 종료하는 장치도 아닙니다.

## 새 대화에서 이어 가기

같은 프로젝트 폴더에서 새 대화를 열고 `docs/specs/<goal> 이어서 해줘`라고 보냅니다. Seal이 목표·계획·진행 기록과 현재 상태를 읽고 남은 일을 이어 갑니다. 사용자 판단이 필요한 항목이 남아 있으면 먼저 답합니다.

## 소스의 검증 근거 보고

Seal 0.1.10 소스 형식은 기대 결과의 근거, 실제 관측 경계, 시험 방법과 대체 환경을 구분합니다. 같은 근거는 조건 그룹으로 참조할 수 있습니다. 검토에는 예정, 완료·중단 보고에는 실제 결과와 미관측·남은 위험을 남깁니다. 실제 실행은 정답 근거 자체가 아니며 fake 결과가 실제 모델 관측으로 바뀌지 않습니다. 시각 출처와 판단을 바꾼 새 사실도 구별합니다.

기존 목표는 시작 형식을 유지하고 누락된 새 항목은 미기록입니다. 과거 완료를 덮어쓰거나 관측을 채우지 않습니다. 이 소스 계약 설명은 현재 배포판 v0.1.3·seal 0.1.9 설치를 바꿨다는 뜻이 아닙니다. [가상 보고 예시](../examples/verification-reporting.md)를 참고하세요.

## 소스의 보증 정책

Seal 0.1.11 소스는 목표나 프로젝트가 명시한 보증 정책의 필수 범위를 조건에 연결합니다. 필요한 독립 검토·실제 경계 근거가 없으면 완료 보류하며, 무관한 작업은 계속할 수 있습니다. 선택 비교는 미관측과 한계를 남깁니다. 모델·실행 순서는 실행자가 정하고 Core는 검토 동의를 충분성으로 판정하지 않습니다. [가상 보증 사례](../examples/verification-design.md)는 계약의 연결 예시이며 실제 모델 관측이 아닙니다.
