# 에이전트 호출: 로그인 실패 문구

평가용 가상 시나리오입니다. 실제 사용자 대화나 실행 기록이 아닙니다([설명](README.md)).

Status: 초안(사람 확인 전)

## 요청

"로그인 실패 문구 바꾸는 거 jaekit으로 해줘. 지금은 '오류가 발생했습니다'만 나와서 뭘 고쳐야 할지 모르겠대"

## 저장소 맥락

- 로그인 화면(`src/auth/LoginForm.tsx`)은 로그인에 실패하면 "오류가 발생했습니다"만 보여 준다.
- 로그인 API(`src/auth/login.ts`)는 비밀번호가 틀려도, 계정이 없어도 같은 오류 코드 `AUTH_FAILED`를 돌려준다.
- 보안 문서(`docs/security.md`): 화면 문구로 계정이 있는지 알 수 있게 하지 않는다.
- 같은 동작을 다루는 목표 문서는 없다.

## 대화 맥락

- Spec을 설치한 새 대화에서 돌린다.
- 사용자는 Spec을 직접 부르지 않는다. `/spec:spec`, `$spec:spec`, `@Spec` 없이 "요청"을 그대로 보낸다. 호스트 에이전트가 요청을 보고 Spec을 부른다.

## 사용자 답

- 그 밖의 질문: 알아서 정해 줘

## 기대 결과

- 물어야 할 것
  - 없음. 계정이 있는지 드러내지 않는다는 결정은 보안 문서에 있으므로 출처와 함께 쓴다
- 묻지 않아야 할 것
  - 목표 문서를 저장해도 되는지(저장 동의)
  - 새 문구의 정확한 표현과 화면 위치 같은 구현자가 정할 세부
- 들어가야 할 조건(필수)
  - 비밀번호가 틀리거나 계정이 없으면 로그인 화면에 같은 새 문구가 나오고, 그 문구로 계정이 있는지 알 수 없다
  - **유지**: 로그인에 성공하는 흐름은 그대로다
- 끝난 모습
  - 첫 응답에서 `docs/specs/<goal>/SPEC.md`를 바로 쓴다. 대화로 요약만 보여 주고 파일 쓰기를 미루지 않는다
  - 문서는 `Status: Draft`이고, 첫 `##` 앞에 `Proposed-By: agent` 줄과 제안한 등급(`Assurance: light`)이 한 번씩 있다
  - 결정과 이유에 에이전트가 Spec을 부른 근거로 사용자의 말 인용("jaekit으로 해줘")이 있다
  - `## Open Decisions`에 사용자가 이 제안을 받아들이는지가 한 항목으로 있다
  - 보고에 등급과 고른 이유가 있고, 끝에 구현 여부 질문이 따로 한 번 있다. 질문은 목표 경로와 등급을 밝히고 "응"이 제안의 수락도 된다고 말한다
  - 에이전트가 사용자 대신 제안을 받아들이거나 `Ready`로 바꾸라고 해도 문서는 `Draft`로 남는다
  - Spec이 멈출 때까지 목표 문서 밖의 변경이 0이다
- 들어가면 안 되는 것
  - 로그인 시도 횟수 제한, 비밀번호 재설정 안내, 다국어
- 질문 상한: 0
