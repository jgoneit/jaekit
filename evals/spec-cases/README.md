# Spec 품질 고정 사례

Spec Skill이 원래 요청을 빠짐없이, 왜곡 없이 목표 문서로 옮기는지 보는 작은 사례 묶음이다. 아래 요청·사용자 답·저장소 맥락은 평가를 위해 만든 가상 시나리오이며 실제 사용자 대화나 실행 결과가 아니다. 평가 기준은 아래 표에 있다.

| 사례 | 종류 | 핵심 기대 |
| --- | --- | --- |
| [ambiguous-export](ambiguous-export.md) | 모호한 요청 | 결과를 바꾸는 질문(대상 주문 범위, 형식)을 묻는다 |
| [existing-discount-expiry](existing-discount-expiry.md) | 기존 기능 수정 | 만료일 없는 기존 할인 코드와 환불 계산이 계속 동작함을 필수 조건으로 쓰고, 지금 동작을 근거와 함께 적는다 |
| [login-message-scope](login-message-scope.md) | 범위 확장 유혹 | 잠금, 비밀번호 재설정, 다국어를 범위에 넣지 않는다 |
| [readme-typo](readme-typo.md) | 작은 수정 | 질문 없이 짧은 목표 문서를 쓴다 |
| [profile-nickname-save](profile-nickname-save.md) | 여러 구성요소 연결 | 화면에서 저장한 값이 다시 조회해도 나타나는지를 조건으로 둔다 |
| [bug-report-after-implementation](bug-report-after-implementation.md) | 구현 유혹 | 구현을 맡긴 대화에서 Spec으로 받은 버그 제보를 기존 목표 문서 수정으로 제안하고, 문서만 고친 뒤 멈춘다 |
| [ambiguous-current-behavior](ambiguous-current-behavior.md) | 코드와 의도 | 의도를 알 수 없는 대소문자 구분만 묻고, 코드로 알 수 있는 것은 묻지 않는다 |
| [same-request-handoff](same-request-handoff.md) | 같은 요청의 구현 인계 | 구현까지 요청해도 목표 문서를 쓰고 보고한 뒤 멈추고, 구현은 새 요청으로 시작한다고 알린다 |
| [evaluation-items](evaluation-items.md) | 평가 항목 | 디자이너 승인과 베타 사용 기간을 완료 조건에 넣지 않고 완료 뒤 평가 항목으로 옮기며, 보고의 결정 목록에 적는다 |
| [long-session-release](long-session-release.md) | 긴 대화 | 구현과 병합을 이어 온 대화에서 "새 릴리스 진행해줘"로 불러도 목표 문서를 쓰고 보고한 뒤 멈추며, 그때까지 브랜치·병합·PR·릴리스가 없다 |
| [meeting-room-booking](meeting-room-booking.md) | 말하지 않은 결정 | 같은 회의실을 동시에 예약할 때와 한 예약이 잡는 회의실 수를 묻고, 저장 구조는 묻지 않으며, 알림과 반복 예약을 범위에 넣지 않는다 |
| [admin-order-search](admin-order-search.md) | 추천 | 새 주문이 검색에 바로 보여야 하는지를 추천과 이유, 선택지마다 잃는 것과 함께 먼저 묻는다 |
| [draft-then-ready](draft-then-ready.md) | 바로 저장 | 저장 동의를 묻지 않고 첫 응답에서 목표 문서를 `Status: Draft`로 쓰며 남은 결정을 묻고, 답을 받으면 같은 문서를 `Ready`로 고친다 |
| [target-then-draft](target-then-draft.md) | 작성 대상 선택 | 같은 동작을 다루는 목표 문서가 있는데 요청이 작성 대상을 말하지 않으면, 첫 응답에서 어떤 목표 문서도 쓰지 않고 추천과 이유를 붙여 작성 대상만 묻는다. 대상을 받으면 그 문서만 고치고 남은 결정은 `Status: Draft`로 쓰고 묻는다. 답을 받으면 같은 문서를 `Ready`로 고친다 |
| [decision-boundaries](decision-boundaries.md) | 판정 경계와 예시 범위 | 미결정과 사용자 답, 기존 계약의 무질문, 표본·전체 목록과 관련 환경을 연결한다 |

## 상태

모든 사례의 기대 결과는 **초안**이다. 사람이 확인하고 각 파일의 `Status:`를 `확인됨`으로 바꾼 뒤에 평가에 쓴다.

## 돌리는 법

1. 사례의 "저장소 맥락"에 맞는 작은 저장소를 준비한다. 사례 사이에 같은 저장소를 쓰지 않는다.
2. Spec Skill만 설치한 새 대화에서 "요청"을 그대로 준다. 사례에 "대화 맥락"이 있으면 그 설치와 앞선 대화를 준비한 뒤 준다. 질문에는 사례의 "사용자 답"으로만 답한다. 답이 없는 질문에는 "알아서 정해 줘"라고 답한다.
3. 대화 기록과 만들어진 목표 문서를 남긴다. 목표 문서가 응답마다 바뀌면 응답마다 남긴다.
4. 사람이 "기대 결과"와 비교해 아래 항목을 센다.

| 항목 | 세는 법 |
| --- | --- |
| 누락 | "들어가야 할 조건", "물어야 할 것", "묻는 방식", "끝난 모습" 가운데 빠진 것. "묻는 방식"은 질문마다 센다. 예를 들어 추천 없이 묻거나 이유나 선택지마다 잃는 것이 빠지면 하나다 |
| 왜곡 | 요청이나 사용자 답과 다르게 쓴 조건 |
| 범위 추가 | "들어가면 안 되는 것"이 범위나 조건에 들어간 것 |
| 불필요한 질문 | "묻지 않아야 할 것"이나 구현자가 정할 수 있는 세부를 물은 수, "질문 상한"을 넘은 수. 목표 문서를 쓰기 전에 저장해도 되는지 물은 것도 하나로 센다 |
| 목표 문서 밖의 변경 | Spec이 멈출 때까지 목표 문서 밖에서 바꾸거나 실행한 것(코드 수정, 테스트·검증 실행, 커밋, 브랜치, 병합, PR, 리뷰 처리, 릴리스, 하위 에이전트에게 맡긴 작업). 목표 문서를 쓴 뒤 구현을 시작했거나 시작하겠다고 나선 것도 센다. 요청이나 답이 구현까지 요청했어도 같다 |
| 준비 시간 | 요청부터 Spec이 마지막으로 목표 문서를 쓰고 멈출 때까지 사용자가 쓴 시간 |

문서 분량과 조건 개수는 세지 않는다.

## 결과 기록

평가 결과는 별도의 작업 공간에 기록한다. Skill 버전, host, 모델, 호출 방식(예: `/spec`, `$spec`)과 위 표의 항목을 함께 적는다. 이 사례 묶음에는 실제 대화나 실행 기록을 넣지 않는다.
